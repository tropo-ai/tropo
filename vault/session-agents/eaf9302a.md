# sa.daily-vault-health

*One-shot reporter. Synthesizes vault health into a crew orientation briefing, terminates.*

## Purpose

Produce `shared/orientation/daily-health-report.md`. This file is the crew's morning briefing — loaded at boot by executives to get oriented without reading a dozen source files. Keep it under 400 words. Be factual.

## Report Sections

### 1. Vault Status
Overall: CLEAN / WARNING / BLOCKING. One sentence. Based on what you find below.

### 2. Blocking Issues
Anything preventing an agent from booting or working normally. Check:
- FLASH-severity events: `python3 vault/tools/tropo-query-events.py --severity flash --limit 20`
- Blocked tasks with stale blockers, derived from `vault/00-index.jsonl` (§3)

**A FLASH is UNRESOLVED only if nothing has closed it.** A FLASH is CLOSED when a later event carries `correlationid: <flash-id>` and `data.resolves_flash: true`. Filter those out before reporting — otherwise every FLASH ever raised is reported as open forever, the count only grows, and the section becomes noise readers learn to skip.

```bash
# unresolved = flash ids with no correlated resolves_flash event
python3 - <<'EOF'
import json, subprocess
def q(*a): return json.loads(subprocess.run(["python3","vault/tools/tropo-query-events.py",*a],capture_output=True,text=True).stdout or "[]")
flash = {e["id"] for e in q("--severity","flash","--limit","200")}
resolved = {e.get("correlationid") for e in q("--type","tropo.broadcast.crew","--limit","500")
            if isinstance(e.get("data"),dict) and e["data"].get("resolves_flash")}
print(sorted(flash - resolved))
EOF
```

If none: "None."

*(v1.1 vela-v68 2026-07-19: resolution semantics defined here for the first time. Six FLASHes had sat "unresolved" — five from a transient 2026-07-08 git-index corruption whose activations were already retired and whose flag files were already gone, and one v1.62 false-ship alarm 22 releases stale. All were resolved in fact; none could ever be closed because no convention existed to close them.)*

### 3. Vault Health
Derive from `vault/00-index.jsonl` — the live index, regenerated by `tropo-rebuild-vault.py`. Report:
- Tasks `status: done` with no verifier (count) — **`status:`, not `state:`**. `state:` is lifecycle (uniformly `active` for live records); `status:` carries workflow. Reading `state: done` returns 0 forever.
- Orphan tasks with no `member_of` project (count)
- Blocked tasks — entries carrying a `blocked-by` relationship (count)
- Index freshness: the modification time of `vault/00-index.jsonl`

If the index is older than 24 hours, flag as WARNING — run `tropo-rebuild-vault.py` and note it in the report.

*(v1.86 repoint, vela-v68: this section previously read `vault/00-integrity.json` for the counts and `vault/00-graph-registry.jsonl` for the rebuild timestamp. Both are retired frozen surfaces — see §Retired surfaces.)*

### 4. Crew Status Staleness
Check `00-crew-brief.md` plus every active agent's status card. **Do not hardcode UIDs** — iterate the crew roster instead (P0.4 fix; v1.69 roster-iteration):

1. Read `00-crew-brief.md` — the crew table lists each active agent with their unified-entry UID in the format `(status card: [uid](vault/agents/<uid>.md))`. Note the path is `vault/agents/`, **not** `vault/files/` — identity lives in the v1.69 unified entry.
2. For each active agent in the table, read their unified entry at the linked path and check the **`last_session`** field in frontmatter. (There is no `last_updated` field on these entries — checking for it silently yields nothing.)
3. Flag any status card not updated in more than 48 hours as WARNING.

On-hold agents (any agent explicitly marked on-hold in the crew table): flag as INFO, not WARNING.

### 5. Event-Log Health
Crew channels were retired at v1.61 (events.capsule Rule 13); the event log is the canonical coordination surface. Check:
- Recent crew activity: `python3 vault/tools/tropo-query-events.py --type tropo.broadcast.crew --limit 10` — note the most recent broadcast date. Nothing in 72h is worth an INFO line (a quiet crew, not necessarily a fault).
- Unresolved FLASH-severity events (same query as §2) — any open one is a WARNING.
- Dangling threads: for each active agent, read their `party_uid:` from their unified entry (already resolved in §4), then `python3 vault/tools/tropo-query-events.py --party <their-party-uid> --since-id 0 --type tropo.message.sent --limit 50` (read-only — **do NOT pass `--update-cursor`**) and scan the results for `reply_required: true` events with no later event carrying `correlationid: <that-event-id>`. Flag any agent carrying unanswered threads. **`--since-id 0` is load-bearing, not optional:** `--party` defaults its `since_id` to that agent's saved cursor, and every cursor sits near the head of the log, so the command without it returns an empty result for every agent and reports a clean board that is not clean.
- **SQLite projection completeness (v1.9 addition, backstop for the emit-time auto-heal):** `python3 -c "import sys; sys.path.insert(0,'vault/tools'); from lib import event_identity; from pathlib import Path; events=event_identity.load_event_union(Path('.')); print(event_identity.sqlite_projection_complete(Path('vault/events/00-events-index.sqlite'), events))"` (run from vault root — `sys.path.insert` must precede the `lib` import). If it prints `False`, the derived SQLite cache has diverged from the canonical log — run `python3 vault/tools/tropo-rebuild-events-sqlite.py` to heal it, and surface a WARNING line either way (healed-today vs. found-clean). **Why this check still exists now that the tools self-heal (v1.10, 2026-07-31):** healing is triggered by *detection*, so it fires when someone emits, drains, or queries — which covers essentially every real divergence, including the merge-induced ones the old emit-only heal missed entirely. What it does NOT cover is a genuinely silent studio: if nobody touches the event log at all, nothing detects and nothing heals. This daily check is the bounded backstop for exactly that case, and it is also the one observer that reports the *state* rather than just fixing it — a `False` here on a busy day means the heal itself is failing, which is a real finding worth escalating rather than quietly re-running. *(Pre-v1.10 this bullet's rationale was "the emit-time heal only fires on the NEXT emission"; that gap is now closed on the read path, so the backstop's job narrowed from covering-quiet-periods-after-any-divergence to covering-total-silence.)*

**NEVER run `tropo-check-events.py --as <another-agent>`.** It is not read-only — it advances that agent's own read cursor and writes a read-receipt under their identity for events they never actually saw, which then silently makes them miss those threads at their own next boot. `tropo-query-events.py --party <uid>` (without `--update-cursor`) is the safe read-only equivalent; only `--as <yourself>` on your own axis ever advances a cursor legitimately.

*(v1.86 repoint, vela-v68: replaced the `channels/ops.md` + `channels/alerts.md` size/ceiling checks — both retired at v1.61 Rule 13, so this section had been measuring files that no longer exist. Filed as defect (2) of `524163ed`.)*
*(v1.87 fix, vela-v69, 2026-07-21: the dangling-threads check above previously instructed `tropo-check-events.py --as <agent>` for every OTHER active agent — this fired for real on this dispatch and advanced/fabricated read-receipts for Talos, Metis, Orpheus, Argus, and Po, reverted immediately (uncommitted). This is the exact hazard V68 caught and reverted live on 2026-07-19 (memory `ad0bc394`) — it had never been fixed at the source, only recovered from after the fact. Replaced with the `--party` read-only query, which was already the documented safe alternative in agent memory but had not been back-ported into this spec.)*
*(v1.9 addition, vela-v69, 2026-07-25, Mike-directed root-cause fix: the SQLite events-index projection sat silently ~2 days stale (6625/7578 events) with no self-heal and no alerting beyond a stderr warning nobody was watching.
