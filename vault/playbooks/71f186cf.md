# Apply a Tropo-OS Update

*The generic update installer. Installed once per vault. Every future update flows through it.*

*This playbook is executed by the concierge after it detects a `tropo-update-*` folder in `vault/updates/pending/` and the user has approved the update. It is the runtime that reads an update's `manifest.yaml` and applies each operation against the vault.*

## Intent

Apply a Tropo-OS update package to this vault safely, verifiably, and with honest recovery if anything fails. The user trusted the update by dropping it into `pending/` and approving it (for v1.1+ updates with migrations, approval includes explicit acceptance of the dry-run diff shown at review). Your job is to execute the manifest exactly, run any migrations against user content in commit mode, verify the result via the update's own test playbook, write the covenant verification receipt, and leave an honest record — in `applied/` if everything passed, in `failed/` with a full report if anything did not.

The update was written by someone who knew what they were doing. You are not deciding whether the update is a good idea — that decision already happened. You are the executor. Follow the manifest. Do not improvise operations. Do not skip verification. Do not update `.tropo/version.md` unless verification passed.

**v1.1 note: Dry-run is the concierge's responsibility, not yours.** Before you are activated, the concierge has already invoked each migration playbook in dry-run mode, aggregated the diffs, presented them to the user, and captured explicit user approval. Your job is the commit phase — execute the discrete operations the user saw, run the migrations in commit mode against the same vault state, and detect any divergence from the dry-run diff the user approved. If the commit diff diverges from the dry-run diff (vault state changed between review and commit), halt — the user did not approve whatever you would actually do.

**v2.0 note: the covenant is the point.** Every operation you execute is judged against one property: does it touch a user file? The namespace predicate decides this by filename alone, before any content is read. Section "The Namespace Predicate" below is the single most important thing in this file — read it before Step 3.

## Suggestions

- Read the `UPDATE.playbook.md` before you read the `manifest.yaml`. The playbook tells you *why*. The manifest tells you *what*. Knowing the why makes the what legible.
- Log every operation and every migration as you go, not at the end — a crew event (**`python3 vault/tools/tropo-emit-event.py --type tropo.broadcast.crew --source /tools/update-walk --lifecycle ephemeral ...`**; `channels/ops.md` retired v1.61 per events.capsule Rule 13). If the apply halts mid-flight, the event log is the user's breadcrumb.
- When an operation touches an existing file, read the current file first and diff mentally against the incoming content. If the diff is nothing (the file is already at the target state), log it as a no-op rather than a failure.
- For migrations, the dry-run report from the concierge's review pass is authoritative. Your commit-phase migration run MUST match it. If a file the dry-run said would change no longer matches that expectation, halt the migration — the user approved the dry-run diff, not the new state.
- Unexpected file structure inside a migration's scope is **not** a failure. Log-and-skip per §14.3. Failures-to-halt-on are: malformed migration playbook, filesystem errors, governance boundary violations.
- Speak plainly to the user. Use the update_type to frame the message ("this feature update", "this security fix"), not the word "patch" as a synonym for "update."
- When in doubt about an operation's intent, re-read `UPDATE.playbook.md`. The narrative should disambiguate.
- When in doubt about whether a path is REPLACE or PRESERVE, do not guess — apply the namespace predicate exactly as written. It is designed to never need judgment.

## The Namespace Predicate (v2.0 — read this before Step 3; LOCK-AMENDMENT 2 added category (d))

This replaces the v1.1 SHA-drift / seed-propagate heuristic (old Step 3c) entirely. The heuristic guessed what was user-owned by comparing file *content*. One Home (ADR-045 [ca6e5824](../files/ca6e5824.md)) makes that guess unnecessary for most of the vault: a path's ownership is determined by its **filename namespace** — plus, for the update mechanism's own files, by the studio's own shipped manifest (LOCK-AMENDMENT 2, below).

**The rule — four categories** (Orpheus O25 finding at the One-Home doc-spec close, 2026-06-28, corrected the earlier two-category framing that wrongly treated `.tropo/` as a preserve-only pointer; LOCK-AMENDMENT 2, 2026-07-02, added category (d) after finding [4496553c](../files/4496553c.md) — see "Why category (d) exists" below):

| Category | Pattern | Behavior |
|---|---|---|
| (e) Derived index surface | EXACTLY `vault/00-index.jsonl`, `vault/00-archive-index.jsonl`, `vault/00-index.sqlite`, `vault/00-project-tree.jsonl` | **REGENERATED** — neither prompt nor write, in any branch. These are manifest-listed and never hash equal to what shipped, because the rebuild regenerates them on the way past; category (d) therefore read them as USER_MODIFIED_SHIPPED and asked the user to approve overwriting a file they never touched. That prompt has no honest answer — "keep mine" and "take theirs" are both wrong for an artifact Step 4.4 settles anyway. **The Step 4.4 rebuild is the sole writer.** Exact paths, never a prefix: `vault/00-` is a namespace a governed file could join tomorrow. (LOCK-AMENDMENT candidate, d220d43b D9, Argus A146 concurrence 2026-08-08.) |
| (a) OS component | Under `vault/` at ANY depth, basename starts with `tropo-` (e.g. `vault/tropo-rebuild-vault.py`, `vault/tools/tropo-validate.py`, `vault/tools/lib/tropo_update_namespace.py`) | **REPLACE** — this is the shipped standard library; updating it is the whole point. |
| (b) Bootstrap floor | anything under `.tropo/` (boot config, the OS P0 primitives SELF-HEALING/HUMAN-NAVIGATION, schema, generated catalogs, concierge, orientation) | **REPLACE** — this is ALSO shipped OS, just not under `vault/` and not `tropo-*`-named. It is not a preserve-only pointer tree. |
| (c) User/studio content | `vault/<slug>-<uid>.md` or bare `vault/<uid>.md`, or anything not positively matching another category | **PRESERVE** — never touched, except by a migration the user has explicitly approved via the dry-run-diff gate. The default. |
| (d) Manifest-listed OS substrate | any path listed in the studio's own shipped `MANIFEST.md` | **REPLACE** if the on-disk hash matches the manifest's recorded SHA-256. **`USER_MODIFIED_SHIPPED`** if it doesn't — never silently overwritten; surfaced as an explicit overwrite-confirm line in the dry-run diff instead (see "Handling category (d) drift" below). |

**Why category (d) exists.** Categories (a)–(c) alone cannot classify the update mechanism's *own* files: canonical UID-named playbooks (this file, `71f186cf.md`, is one), UID-named tools, `.tropo-studio/` registries, and root docs (where the ADR-049 covenant text lands) are neither `tropo-*`-named nor under `.tropo/` — under the three-category rule they defaulted to PRESERVE, which meant an update could never deliver its own machinery to an existing studio. Found 2026-07-02 by Argus running the real v1.77→v1.78 machinery delta through the real predicate while staging the Po walk (board item [4496553c](../files/4496553c.md)) — the floor test's original idealized fixture (seeded only `tropo-*`-named files) could not see this gap. Mike locked the fix verbatim ("lock it. let's do it.").

**The reference implementation is code, not prose:** [`vault/tools/lib/tropo_update_namespace.py`](../tools/lib/tropo_update_namespace.py) — `classify(rel_path, manifest_index=None, current_hash=None)` returns `REPLACE`, `PRESERVE`, or `USER_MODIFIED_SHIPPED`; `parse_manifest_md(text)` parses the studio's own `MANIFEST.md` into the `manifest_index` this needs. Both the apply engine (this playbook, conceptually) and [THE FLOOR TEST](d2efcac9.md) import the *same* module — the predicate cannot drift between "what the playbook says" and "what actually gets tested," because there is only one implementation. (`is_os_component(rel_path)` remains as a narrower, manifest-free helper covering categories (a)/(b) only, for callers that don't have a manifest handy.)

**You MUST decide replace-vs-preserve-vs-user-modified-shipped by looking at the filename and, for category (d), the manifest — never by reading file content to guess intent.** If a path is not recognizably category (a), (b), or manifest-listed, it is PRESERVE by default — replace must be earned, never assumed.

**Handling category (d) drift (LOCK-AMENDMENT 2; hard-stop structural at LOCK-AMENDMENT 3).** When a manifest-listed path's on-disk SHA-256 doesn't match the manifest, the file is OS substrate the owner has locally edited. This is content the owner chose to touch — the update MUST NOT clobber it silently. At Step 3 (discrete operations), a `USER_MODIFIED_SHIPPED` classification (and, per LOCK-AMENDMENT 2 F3, an `add`-operation target collision with genuine unlisted content) routes to the **Confirm Hard-Stop** below instead of auto-applying. This is a standalone Step-3 gate, independent of whether the update has migrations; it does NOT require `manifest.migrations` to be non-empty, and it is separate from (composes alongside, when both are present) the concierge's migration-specific Review-phase dry-run at Section 5.

## The Confirm Hard-Stop (v2.3 — LOCK-AMENDMENT 3, finding 5d4bbbf2 F1-confirm)

**The Po-walk finding this section fixes:** in the walk that produced LOCK-AMENDMENT 3, the concierge bypassed two per-file overwrite-confirms by reasoning that the user's earlier blanket "go ahead and apply" covered them ("redundant per-file prompt"). The outcome was harmless (both files were OS substrate, not user content) — but an agent's *judgment call* overriding a designed per-item stop is exactly the behavior class the covenant forbids, regardless of outcome. Prose telling the next agent "don't do that" is not a fix; it is the thing that already failed once.

**The reference implementation is code, not prose:** [`vault/tools/lib/tropo_update_confirm_gate.py`](../tools/lib/tropo_update_confirm_gate.py) — `ConfirmGate`. Every path that classifies `USER_MODIFIED_SHIPPED`, or that collides on an `add` target with unlisted content (LOCK-AMENDMENT 2 F3), is `register()`-ed as a needs-confirm item the moment Step 1b/Step 3 discovers it. **You MUST call `require_cleared(path)` before executing that operation.** `require_cleared()` raises `ConfirmNotRecordedError` unless *that exact path* has an explicit, recorded, `approved` acknowledgment on file — present the overwrite-confirm line to the user (*"`<path>` is a shipped file you've modified locally [or: something already exists at `<path>` that isn't part of your shipped install]. Overwrite with the update's version? [Your local changes will be lost if you say yes.]"*), capture the user's per-file yes/no, and call `record_ack(path, "approved"|"declined")` with the exact path before calling `require_cleared(path)` again.

**There is no bulk-approve method on `ConfirmGate` by design.** A single "the user approved the whole apply" cannot satisfy `require_cleared()` for an individual path — the class has no API surface that would let it. If you find yourself wanting to treat a blanket approval as covering a per-item confirm because it "feels redundant," that feeling is the covenant violation forming — stop and present the per-file prompt anyway. On `declined`, skip that single operation and note the skip in the apply report; do not halt the whole update over one declined confirm (same posture as an `add`-collision decline today).

Because cross-references resolve by UID and the `tropo-` token is a display/filename convention (ADR-045 Decision §3, OP-12 name≠address), and the manifest is content-blind + deterministic + constructed at build time, this predicate is still a **one-line-per-file rule, never a content diff to decide intent.** "User files are sacred" (Update Spec v1.0 §3.3) stops being a hopeful heuristic and becomes a structural guarantee — now covering the update mechanism's own files too.

## Rules

**Manifest validation (v1.0, unchanged except migration-list validation in v1.1):**

- **You MUST validate `manifest.yaml` before executing any operation.** Required fields: `version`, `update_id`, `update_type`, `target_version`, `min_compatible`, `summary`, `released`, `author`, `operations`, `verification`. If any are missing or malformed, halt and report to the user with the list of missing fields and the expected shape. Do not execute. When reporting, include this example so the author can fix quickly:
 ```yaml
 # Required manifest shape:
 version: 1
 update_id: "tropo-update-v0.X.X"
 update_type: "patch|feature|release|security"
 target_version: "0.X.X"
 min_compatible: "0.X.X"
 summary: "One-line description"
 released: "YYYY-MM-DD"
 author: "author-name"
 operations: [...]
 verification:
 test_playbook: "TEST.playbook.md"
 runner: "vault-steward"
 on_failure: "halt"
 ```
- **You MUST validate the `migrations:` list if present (v1.1).** Each migration entry must have `path`, `scope`, and `reason`. The migration playbook file must exist at `files/<path>` inside the update folder. The migration playbook must itself conform to Playbook Spec v1.0 (six sections). If any migration entry is malformed or the playbook file is missing, halt.
- **You MUST accept the reserved slots `conditionals:`, `interactives:`, and `hooks:` without executing them (v1.1).** If the manifest declares any of these with a non-empty value, log one line: `[update_id] v1.1 reserved slot declared but not executed: <slot-name> (<count> entries)`. Then proceed as if the slot were empty. Do NOT attempt to execute entries in any reserved slot — the execution contract is not defined in v1.1 and forward compatibility depends on the slot being parseable-but-inert.

**Compatibility (v1.0, refined in v1.1, hardened in v2.0):**

- **You MUST verify `min_compatible` against `.tropo/version.md` before executing.** If the vault's current version is lower than `min_compatible`, halt. The halt message MUST include plain-language version gap guidance: name the specific intermediate versions the user needs to install in order before this update can apply. A bare "incompatible" refusal is a wall; a named sequence is a path.
- **v2.0 addition — the apply-time incompatibility halt is a Step 0.5 pre-flight check, before Step 1 manifest validation.** If a version manifest (from the Update API — see [`vault/tools/tropo-generate-update-manifest.py`](../tools/tropo-generate-update-manifest.py)) was already consulted at Review and carries `migration_required: true`, deliver that manifest's `message` field **verbatim** and halt cleanly — before any operation, before manifest validation even runs. This is the front-door version gate (caught at check-time by the concierge's boot-time Update API check); the `min_compatible` check in this section remains the apply-time backstop for the case where no Update API manifest was consulted (e.g. offline, or an update dropped in directly). Both gates produce plain-language version-gap guidance; neither is optional.

**User files (v1.0, superseded by the Namespace Predicate above — kept here for the discrete-operations detail):**

- **Discrete operations (`add`/`replace`/`edit`/`move`/`delete`) apply ONLY to paths the Namespace Predicate classifies as OS components** (category (a) — under `vault/` at any depth with a `tropo-` basename — or category (b) `.tropo/*`). An operation whose `path:` does not classify as an OS component is a manifest authoring error — halt and report it; do not execute it "just this once." The one exception is a **migration**, which may touch user content under the rules below, because the user explicitly approved its declared scope.

**Migrations (v1.1, new; scopes re-homed at v2.0):**

- **Migrations MAY walk user workspace content and governance files under `vault/`; MUST NOT touch `.tropo/` or `vault/tropo-*`.** Migrations are the class of operation for cross-cutting changes to existing user content. The OS components (both categories (a) and (b) of the Namespace Predicate) are the discrete-operations' domain. A migration that attempts to write an OS-component path is a governance boundary violation — halt and classify as `governance` in the failure report.
- **The user's approval of an update with migrations temporarily authorizes the declared scopes.** Individual agent `scope.writes` boundaries do NOT block a user-approved migration's declared scope for the duration of the commit run. Every such write is logged to the migration report for audit.
- **You MUST follow the concierge's dry-run report, not recompute the scope independently.** Before you were activated, the concierge ran each migration in dry-run mode and captured a diff the user approved. Your commit-phase execution MUST produce the same diff. If a file the dry-run said would change no longer matches that expectation (vault state changed between review and commit), halt the migration with a divergence error.
- **You MUST log-and-skip on unexpected file structure inside a migration's scope, NOT halt.** Malformed frontmatter, unexpected folder layout, missing required fields — these are content-shape issues, not failures. Record each skip in the migration report with a categorized reason. Continue the migration. A non-zero skip count is still a PASS result.
- **You MUST halt the migration phase on commit failures that are NOT unexpected structure.** Filesystem errors, permission denied, divergence from dry-run, governance boundary violations, or the migration playbook itself being malformed — these are failures. Log to the event log, write the migration report up to the point of failure, and move the update to `failed/` per the halt protocol.
- **You MUST write a migration report per §14.3.2 of Update Spec v1.1** for every migration that runs (dry-run or commit), passing or failing. Location (re-homed at v2.0): `vault/updates/pending/<update_id>/<migration_id>-commit-report.md` during execution, travels with the update to `applied/` or `failed/`.

**Execution order (v1.1 extends v1.0):**

- **You MUST execute operations in the order they appear in the manifest.** Manifest order is meaningful — later operations may depend on earlier ones.
- **You MUST execute migrations AFTER all discrete operations succeed, in manifest order.** Discrete operations prepare the OS components migrations reference (e.g., shipping a new schema doc that migrations use). Migrations that run before those changes land would reference content that doesn't exist yet.
- **You MUST log every operation and every migration to the event log immediately after executing it.** One line per item: update_id, operation index or migration id, type, path or scope, result.

**Halting and state (v1.0, unchanged; paths re-homed at v2.0):**

- **You MUST halt on the first hard failure** (failed validation, failed operation, failed precondition, failed migration commit per above) and move the update folder to `vault/updates/failed/` with a partial-apply report. Do not attempt automatic rollback. Do not continue past a failure.
- **You MUST activate the vault steward after the last operation AND the last migration succeed** and hand it the path to the update's `TEST.playbook.md`. Do not declare success until the steward returns PASS.
- **You MUST NOT update `.tropo/version.md`** until verification returns PASS. Version is the authoritative record of what is installed and working. A partially applied update is not a new version.
- **You MUST preserve the update folder and its verification report in either `applied/` or `failed/`.** Never delete an applied or failed update (per `tropo-recycle.py` soft-delete discipline if it must ever be removed). The history is the audit trail.
- **You MUST NOT send verification reports, receipts, or any part of the update outside the user's vault.** All reports stay local.
- **You MUST update `vault/updates/update-history.jsonl`** with a new row for every applied or failed update. This is a JSONL append — **NOT** a `00-index.md` (that per-folder convention was retired 2026-06-21; see [`vault/updates/AGENTS.md`](../updates/AGENTS.md)).
- **v2.0 — you MUST write a per-apply verification receipt** to `vault/updates/receipts/<update_id>-receipt.md` (ADR-049 covenant layer 3; ACCEPTANCE-mandated). See "The Covenant Receipt" below.
- **v2.3 (LOCK-AMENDMENT 3) — you MUST NOT write to disk after sealing the receipt.** Run post-apply housekeeping (Step 4.4) BEFORE computing (4.5) and sealing (4.6) the receipt, recording every write via `ReceiptSeal.record_write()` as you go. A write attempted after `seal()` is a hard failure the guard itself raises — do not catch and ignore `PostReceiptWriteError`; if you see it, the step order is wrong and must be fixed, not worked around.
- **v2.3 (LOCK-AMENDMENT 3) — you MUST NOT execute a `needs_confirm` operation without a recorded per-item `ConfirmGate.require_cleared(path)`.** A blanket "the user approved the apply" does not and cannot satisfy this for an individual path — see "The Confirm Hard-Stop" above.
- **New files created by `add` operations MUST have a `uid:` in frontmatter (if they have frontmatter at all)**, per matched-primitives topology ([adac1f10](../files/adac1f10.md)): entries land at `vault/files/<uid>.md` and project into `vault/00-index.jsonl` via the rebuilder.

## The Covenant Receipt (v2.0 — ADR-049 layer 3; DUAL-HASH + RECEIPT-LAST at v2.3/LOCK-AMENDMENT 3)

Every apply — success or failure — writes a verification receipt so the owner can audit locally that nothing of theirs changed, without trusting this playbook's word for it.

**THE RULING THIS SECTION ENCODES (Mike, 2026-07-02, verbatim: "i think i am okay with the nav block. as soon as we start importing work into the studio, it becomes 'governed'"): the covenant protects user CONTENT, not byte-identity.** The studio's own governance chrome (the nav-block renderer, `tropo-generate-relations-header.py`, run as part of post-apply housekeeping) legitimately writes into governed user file bodies — that write is not a covenant violation. What WAS a violation (Po-walk finding 5d4bbbf2, F6) is a receipt that claimed zero churn by BYTE hash while chrome writes had already landed on disk, undetected, because housekeeping ran AFTER the receipt was computed. The fix below is not "stop the chrome from writing" — it's "make the receipt honest about it, and make it structurally impossible to compute the receipt before all the writes it's supposed to cover have happened."

**RECEIPT-LAST — the receipt MUST be the structurally-terminal act of an apply run, for every write within the covenant's scope.** No OS-substrate write, no user-content write, no governance-chrome write happens after it — not a stray cleanup, not a forgotten cache refresh, nothing. (The update's own terminal bookkeeping — version bump, folder move, history append at Step 5A/5B — is the sole, explicitly-named exception: it touches none of what the receipt measures. See Step 4.6.) This is why post-apply housekeeping/index-navigation-rebuild is its own numbered step (4.4, below) that runs BEFORE receipt computation (4.5) and receipt sealing (4.6), not an implicit "on the next rebuild" aside the way earlier versions of this playbook left it (the exact ambiguity the Po walk fell through). **The reference implementation is code, not prose:** [`vault/tools/lib/tropo_update_receipt.py`](../tools/lib/tropo_update_receipt.py) — `ReceiptSeal`. Every write this playbook performs, at every step, MUST call `seal.record_write(path)` at the moment of the write — discrete operations, migrations, AND Step 4.4 housekeeping. Once Step 4.6 calls `seal.seal(receipt_path)`, any further `record_write()` call raises `PostReceiptWriteError` instead of the write silently landing behind the receipt's back. If your execution needs a write after the receipt has been sealed, that need is the bug — stop and fix the step order, do not work around the guard.

**DUAL-HASH RECEIPT — per user file, the receipt reports two different, honest things, not one blended claim:**

1. **The CONTENT hash** (`tropo_update_receipt.content_hash()`) — every user/studio file's content with nav-block spans (`<!-- nav-block:start -->` … `<!-- nav-block:end -->`) canonicalized OUT before hashing. This is the actual covenant proof: "your *words* didn't change," independent of whether the studio's chrome wrote a navigation block into that file this run.
2. **The nav-chrome disclosure list** (`nav_chrome_disclosure`) — an honest, complete list of exactly which files the nav renderer wrote to this run, each with its real post-apply BYTE hash. Nothing here is hidden or folded into the content-hash proof; an owner can audit every one of these files byte-for-byte if they want to.

**File:** `vault/updates/receipts/<update_id>-receipt.md`

**Contents (frontmatter + a short plain-language body — built by `tropo_update_receipt.build_receipt_markdown()`):**

```yaml
---
update_id: "<update_id>"
target_version: "<target_version>"
result: "applied" | "failed"
content_unchanged_count: <N>
content_total_count: <M>
pre_apply_content_hash_manifest: "<combined content-hash fingerprint, category-c files, nav-canonicalized>"
post_apply_content_hash_manifest: "<same computation, after the apply — MUST equal pre_apply on a clean apply>"
content_hash_mismatches: []   # non-empty here is a covenant violation regardless of anything else
nav_chrome_disclosure:
  - path: "<rel path the nav renderer wrote to this run>"
    byte_hash: "<real post-apply sha256 of that file's actual bytes>"
tropo_components_replaced: ["<rel path>", ...]
generated_at: "<ISO 8601 timestamp>"
---
```

The body is a short, plain-language paragraph Po reads aloud at the end of the apply. A clean run reads like: **"your content: 5/5 unchanged; navigation added to 4 files"** — honest and green, never a false zero-byte-churn claim, and never silent about what the studio's own chrome did. If `content_hash_mismatches` is non-empty, this is itself evidence of a covenant violation and the receipt says so explicitly (`**COVENANT VIOLATION**`) rather than silently reporting mismatched hashes.

**Why this lives with the apply, not just the build-time floor test:** the floor test proves the *mechanism* can't violate the covenant, in a controlled seed — including, since LOCK-AMENDMENT 3, an end-to-end simulation with the housekeeping step included (`vault/tools/tests/test_clean_update_floor.py`, `check_e2e_apply_with_housekeeping_and_receipt()`). The receipt proves *this specific apply, on this specific vault*, didn't. Construction (floor test) and demonstration (receipt) are complementary, not redundant — per Operating Principle 10 (Stranger encounter is ship).

1. Read `vault/updates/pending/tropo-update-<id>/UPDATE.playbook.md` — understand the *why*.

## Step 0.5: Apply-time incompatibility halt (v2.0 — task b8f2d6a3)

**This runs BEFORE manifest validation.** If the concierge's Review-phase Update API check (or an `updates-manifest.json` staged alongside the update) already determined `migration_required: true` for this update against the current vault version:

1. Deliver the manifest's `message` field **verbatim** to the user.
2. Halt cleanly. Do not proceed to Step 1.
3. `.tropo/version.md` is unchanged. Nothing partially applied.

No silent failure. No dead end. The message itself is the next step. This composes with the `min_compatible` check at Step 2 below: this is the *front-door* gate (caught at check-time, before an update was even dropped into `pending/`, ideally); Step 2 is the *apply-time backstop* for the case where no Update API manifest was consulted (offline check, or an update dropped in directly without going through the boot-time check).

If no `migration_required` flag is in play (the common case), proceed to Step 1.

## Step 1: Validate the manifest

### 1a: Required top-level fields (v1.0)

Check every required field is present:

- `version: 1`
- `update_id` (must match the folder name)
- `update_type` (one of: `patch`, `feature`, `release`, `security`)
- `target_version` (SemVer string)
- `min_compatible` (SemVer string)
- `summary` (non-empty string)
- `released` (YYYY-MM-DD)
- `author` (non-empty string)
- `operations` (list, may be empty only if `migrations:` is non-empty — an update must have SOMETHING to do)
- `verification` (object with `test_playbook`, `runner`, `on_failure`)

### 1b: Validate operations (v1.0, namespace check added v2.0, category (d) added v2.1)

For each operation, check:

- `type` is one of `add`, `replace`, `edit`, `move`, `delete`
- `path` is a string
- **`path` classifies as `REPLACE` under the Namespace Predicate** (v2.0/v2.1 — see "The Namespace Predicate" above; consult `MANIFEST.md` at the vault root for category (d)). If it classifies `PRESERVE`, halt with classification `governance` — do not execute. If it classifies `USER_MODIFIED_SHIPPED`, do not halt the whole update — `register()` it with the Confirm Hard-Stop (`vault/tools/lib/tropo_update_confirm_gate.py`) and execute it only after `require_cleared(path)` returns cleanly (per-file approval recorded), otherwise skip it and note the skip in the apply report.
- `reason` is a non-empty string
- For `type: add`: `source` points to a file inside `files/` in the update folder
- For `type: replace`: `source` points to a file inside `files/`
- For `type: edit`: `operation` is one of `append_section`, `insert_after_heading`, `replace_block`, `append_list_item`, with the required sub-fields for that mode
- For `type: move`: `from` and `to` paths are both strings, and both classify as OS components
- For `type: delete`: `path` is a string

### 1c: Validate migrations list (v1.1)

If `manifest.migrations` is present and non-empty, for each migration entry:

- `path` is a string pointing to a file inside the update folder (typically `files/.tropo/playbooks/migrations/<migration-id>.playbook.md`). Verify the file exists at that path.
- `scope` is a string (glob pattern) or a list of strings (path list), and resolves under `vault/` — never `.tropo/`, never `vault/tropo-*`.
- `reason` is a non-empty string.
- The migration playbook file itself must conform to Playbook Spec v1.0 — it must have frontmatter with `uid:` and the six required sections (Intent, Suggestions, Rules, Resources, Outcomes, Verification).
- The migration playbook must declare a dry-run mode. (Check by reading the playbook's Intent or Rules for language acknowledging dry-run. This is a soft check — if you are unsure, log a warning but do not halt.)
- Verify the concierge has left a corresponding dry-run report at `vault/updates/pending/<update_id>/dry-run-reports/<migration-id>.md`. If the report is missing, halt — the user cannot have approved a dry-run that wasn't performed.

### 1d: Accept reserved slots (v1.1)

If `manifest.conditionals`, `manifest.interactives`, or `manifest.hooks` are present:

- Parse them but do NOT execute any entries.
- For each non-empty reserved slot, log one line: `[update_id] v1.1 reserved slot <slot-name> declared with <N> entries — parsed and ignored (reserved for v1.2+)`.
- Continue with the rest of validation.

If any check in 1a, 1b, 1c, or 1d fails, halt. Log the validation error with update_id. Tell the user which field failed and where. Leave the update in `pending/`.

## Step 2: Check compatibility

Read `.tropo/version.md`. Compare the current `version:` field against the manifest's `min_compatible`. If current version < min_compatible (SemVer comparison), halt with **plain-language version gap guidance** (v1.1 requirement; apply-time backstop per Step 0.5 note above).

The v1.0 guidance was a bare "you need an intermediate update." That's a wall. v1.1 requires a path. Construct the message as follows:

1. State the current vault version explicitly.
2. State the update's `target_version` and `min_compatible`.
3. Enumerate the SemVer gap between current version and `min_compatible` as a list of versions the user needs to step through.
4. Tell the user where to find updates — the Update API manifest (`vault/updates/updates-manifest.json` locally, or the stable published URL) if reachable; the distribution source otherwise.
5. Explicitly say that once the user drops the missing updates into `vault/updates/pending/`, you can walk them one at a time.

Example message:

> "This update (v0.4.7) requires your vault to be at v0.2.2 or later. Your vault is currently at v0.2.0. You'll need to install the versions between v0.2.0 and v0.2.2 first, in order — that's v0.2.1 and v0.2.2 — before I can apply v0.4.7. (There may also be updates between v0.2.2 and v0.4.7 that you want to install in sequence; I can walk them one at a time once you drop them into `vault/updates/pending/`.) You can find Tropo framework updates at [distribution source]. Want me to check `pending/` for any of those intermediate updates right now?"

Leave the update in `pending/`. Log the compatibility failure with the specific gap named. Do not execute any operations.

## Step 3: Execute operations

For each operation in `manifest.operations`, in order. **Every `path:` was already confirmed to classify as an OS component under the Namespace Predicate at Step 1b — this step trusts that check and does not re-derive it.**

### Operation type: `add`

1. Read the source file at `vault/updates/pending/<update_id>/files/<source>`.
2. Check whether the target `path` already exists on disk.
   - **Does NOT exist:** the common case — nothing to overwrite. Proceed to step 3.
   - **EXISTS (LOCK-AMENDMENT 2, F3):** this is a target collision. Classify it exactly like a `replace` operation would: `classify(path, manifest_index, current_hash)`.
     - `REPLACE` (the existing file matches what the customer's own old manifest already recorded at this path) — proceed to step 3 as a normal overwrite; this was effectively a mis-declared `replace`, not a true new-file `add`.
     - `USER_MODIFIED_SHIPPED` (manifest-listed but hash-drifted) — route through the Confirm Hard-Stop (same as a `replace` op's drift case; see "The Confirm Hard-Stop"). Do not proceed until `require_cleared(path)` returns cleanly.
     - `PRESERVE` (the path is not manifest-listed at all — a genuine collision with content the user created independently) — **user collision.** Never silently overwrite. `register()` it with the Confirm Hard-Stop and surface an explicit overwrite-confirm line: *"The update wants to add a new file at `<path>`, but something already exists there that isn't part of your shipped install. Overwrite it? [Your existing file will be lost if you say yes.]"* Only proceed to step 3 once `require_cleared(path)` returns cleanly (explicit per-item approval recorded); otherwise skip this operation and note the skip in the apply report — do NOT halt the whole update over one collision.
3. Write the file at `path` with the source content.
4. If the file has YAML frontmatter and a `uid:` field, registration happens automatically — vault entries project into `vault/00-index.jsonl` on the next rebuild.
5. Log: `[update_id] op <N>: add <path> — OK` (or `— OK (overwrite-confirmed)` / `— SKIPPED (collision declined)` per step 2's branch).

### Operation type: `replace`

1. Read the source file at `vault/updates/pending/<update_id>/files/<source>`.
2. Check the target `path` DOES exist. If it does not, halt with a failure — `replace` requires the file to exist.
3. Read the current file. If its content already matches the source (no-op), log as a no-op and continue.
4. Otherwise, overwrite the file at `path` with the source content.
5. Log: `[update_id] op <N>: replace <path> — OK` (or `NO-OP` if unchanged).

### Operation type: `edit`

1. Read the target file at `path`. If it does not exist, halt with a failure.
2. Apply the surgical edit based on `operation`:
 - **`append_section`**: append the content in `content:` to the end of the file, preceded by a blank line.
 - **`insert_after_heading`**: find the heading named in `heading:` and insert the content in `content:` immediately after it (before the next heading at the same or higher level).
 - **`replace_block`**: find the block matching `match:` (literal string, not regex) and replace it with `replacement:`. Fail if `match:` is not found or is found more than once.
 - **`append_list_item`**: find the markdown list under the heading named in `list_heading:` and append `item:` as a new bullet at the end of that list.
3. Write the modified file back.
4. Log: `[update_id] op <N>: edit <mode> <path> — OK`

### Operation type: `move`

1. Check `from:` exists. If not, halt with a failure.
2. Check `to:` does NOT exist. If it does, halt with a failure.
3. Move the file from `from:` to `to:`.
4. Log: `[update_id] op <N>: move <from> -> <to> — OK`

### Operation type: `delete`

1. Check `path:` exists. If not, log as a no-op and continue.
2. Record the file's UID and path before deletion (audit trail).
3. Soft-delete the file per Preservation Discipline (`python3 vault/tools/tropo-recycle.py <uid> --reason "removed by update <update_id> op <N>"`) rather than a hard delete.
4. Log: `[update_id] op <N>: delete <path> — OK`

### Halting on failure

If any operation fails:

1. Log the failure: `[update_id] op <N>: <type> <path> — FAIL: <reason>`
2. Write a partial-apply report to `vault/updates/pending/<update_id>/apply-report.md` describing what succeeded, what failed, and the vault's current partial state.
3. Move the entire update folder to `vault/updates/failed/<update_id>/`.
4. Add a failure entry to `vault/updates/update-history.jsonl`.
5. Tell the user plainly what happened, using the `update_type` to frame the message.
6. **Do NOT update `.tropo/version.md`. Do NOT activate the steward. Do NOT run migrations.**
7. End execution.

## Step 3b: Execute migrations (v1.1 — new class; paths re-homed at v2.0)

*This step runs only if `manifest.migrations` is non-empty. Skip to Step 4 if there are no migrations.*

*This step runs ONLY after every discrete operation in Step 3 has succeeded.*

### Pre-conditions

1. Confirm `vault/updates/pending/<update_id>/dry-run-reports/` exists and contains one file per migration in `manifest.migrations`. If any are missing, halt with a `governance` classification.
2. Confirm you have write permission to each migration's declared scope. If a scope glob points to a path that does not exist in this vault, log a warning but continue.

### For each migration in `manifest.migrations`, in order:

#### Sub-step 3b.1: Re-run dry-run (divergence check)

1. Read the migration playbook at `files/<path>` in the update folder.
2. Invoke the migration playbook in `dry-run` mode against the current vault state.
3. The migration playbook produces a fresh dry-run report at `vault/updates/pending/<update_id>/<migration_id>-commit-dryrun.md`.
4. Read the concierge's stored dry-run report at `vault/updates/pending/<update_id>/dry-run-reports/<migration_id>.md`.
5. Compare the two reports. Specifically compare the `files_changed` and `files_would_change` sections.

#### Sub-step 3b.2: Handle divergence

If the fresh dry-run diverges from the concierge's stored dry-run:

- Halt the migration phase. Do NOT commit this migration.
- Classify: `content-shape` if the difference is additional files in scope; `migration-logic` if the transformation itself would differ; `governance` if files outside the declared scope are implicated.
- Write a divergence report to `vault/updates/pending/<update_id>/<migration_id>-divergence-report.md` with both diffs side-by-side.
- Log: `[update_id] migration <migration_id> — DIVERGENCE: <classification>, halting migration phase`
- Proceed to the halt protocol at the end of Step 3b.

#### Sub-step 3b.3: Commit the migration

If the fresh dry-run matches the stored dry-run:

1. Invoke the migration playbook in `commit` mode against the current vault state.
2. The migration playbook walks its declared scope, applies the transformation to each eligible file, logs skips with reasons for unexpected structure, and writes a commit report at `vault/updates/pending/<update_id>/<migration_id>-commit-report.md` per the §14.3.2 format.
3. Log: `[update_id] migration <migration_id> — COMMIT OK: <N> changed, <M> skipped, <K> errors`

#### Sub-step 3b.4: Classify the commit result

Read the migration's commit report. Check `result:` field:

- `PASS` with zero errors: succeeded cleanly. Continue to the next migration.
- `PASS` with non-zero skip count: succeeded with defensive skips. Valid success state; pipeline continues.
- `PARTIAL`: partially completed before a halt-worthy error. Halt the migration phase. Do NOT attempt to unwind prior changes.
- `FAIL`: failed outright. Halt the migration phase.

On `PARTIAL` or `FAIL`, proceed to the halt protocol below.

### Halt protocol for migration failures

If any migration fails (divergence, PARTIAL, or FAIL):

1. Log: `[update_id] migration <migration_id> — FAIL: <classification>: <reason>`
2. Write a migration-phase partial-apply report to `vault/updates/pending/<update_id>/migration-apply-report.md`.
3. Move the entire update folder to `vault/updates/failed/<update_id>/`. All migration reports, the divergence report (if applicable), and the concierge's original dry-run reports travel with the folder.
4. Add a failure entry to `vault/updates/update-history.jsonl` with the migration failure classification.
5. Tell the user plainly (framed by `update_type` and the failure classification; the core update files are still in place, the full package moved to `vault/updates/failed/<update_id>/`).
6. **Do NOT update `.tropo/version.md`. Do NOT activate the steward.**
7. End execution.

### On all migrations succeeding

1. Log: `[update_id] migration phase complete: <total> migrations, <changes> total file changes, <skips> total defensive skips`
2. Proceed to Step 4.

## Step 4.4: Post-apply housekeeping — index + navigation rebuild (v2.3 — LOCK-AMENDMENT 3, finding 5d4bbbf2 F6)

**This step MUST run before Step 4.5. This ordering is the entire fix for F6 — earlier versions of this playbook left this as an unsequenced aside ("registration happens automatically... on the next rebuild") with no explicit place in Execution Steps, which is exactly how it ended up running AFTER the receipt in the walk that produced LOCK-AMENDMENT 3.**

1. Refresh the matched-primitive indexes for anything added or changed by Step 3/3b: `vault/00-index.jsonl` (**`vault/tools/tropo-rebuild-index.py --apply`**), `.tropo-studio/registries/agent-registry.yaml`, `.tropo-studio/registries/registry.jsonl` as applicable.
   - **`--apply` is not optional here.** Without it the tool is a dry-run preview (`--apply  Write changes (default is dry-run preview)`), so the seal at sub-step 3 would record index writes that never happened — a disclosure receipt asserting work the disk never saw, which is worse than no receipt. Corrected 2026-08-08; the command had shipped without the flag.
   - Two non-zero exits are expected states, not failures to halt on: a **REFUSAL** naming derivation inputs that changed outside the owned target (run `--apply` again over the full set), and the **shrink ratchet** refusing a record-count drop. `--reconcile` forces full re-derivation but still needs `--apply`; reconcile alone is a no-op.
2. Run the navigation/relations renderer (**`vault/tools/tropo-generate-relations-header.py --write <target> [<target> ...]`** — `target` is a REQUIRED positional; files or directories, and directories are scanned NON-recursively for `*.md`. The bare `--write` this line carried until 2026-08-08 exits on a usage error and renders nothing) over any governed files whose frontmatter changed or that were newly added — this is the step that writes `<!-- nav-block:start -->`/`<!-- nav-block:end -->`-wrapped chrome into governed file bodies, INCLUDING user/studio (category-c) files that reference or are referenced by anything that changed. **This is expected and allowed** (Mike's ruling, above) — it is not a covenant violation. It is exactly the class of write the dual-hash receipt below exists to disclose honestly.
3. **Record every write this step performs via `seal.record_write(rel_path)`, at the moment of the write** — same discipline as Step 3/3b. Keep a running disclosure list of `{path, byte_hash}` for every file the renderer actually touched; you will pass this list into the receipt at Step 4.5.
4. If housekeeping fails partway (a filesystem error, not a routine no-op), treat it as a hard failure: proceed to the halt protocol (move to `failed/`, do not write the receipt as if the run succeeded — write it as a failure receipt instead, still via Step 4.5/4.6, still before any further writes).

## Step 4.5: Compute the covenant receipt (v2.0 — ADR-049 layer 3; DUAL-HASH at v2.3)

Regardless of whether Step 4 returned PASS or FAIL, and only AFTER Step 4.4 has completed:

1. For every category-(c) path present in the vault (the Namespace Predicate's PRESERVE class), compute `content_hash()` (nav-canonicalized) using its content as captured at Step 0 (before any operation ran) as `pre_hash`, and its current on-disk content as `post_hash`.
2. Compute `pre_apply_content_hash_manifest` / `post_apply_content_hash_manifest`: sort the per-file `(path, hash)` pairs, concatenate `path:hash`, hash the concatenation — same construction as the v2.0 receipt, now over content hashes instead of byte hashes.
3. Assemble `content_hash_mismatches`: any path where `pre_hash != post_hash`. **This list MUST be empty on a clean apply** — a non-empty list means user CONTENT changed, not just chrome, which is the actual covenant violation.
4. Assemble `nav_chrome_disclosure` from the running list Step 4.4 built.
5. Call `tropo_update_receipt.build_receipt_markdown(...)` and write the result to `vault/updates/receipts/<update_id>-receipt.md` per "The Covenant Receipt" format above.
6. **If `content_hash_mismatches` is non-empty, this is a hard failure** regardless of Step 4's verdict — see Escalation on Failure.

## Step 4.6: Seal the receipt (v2.3 — LOCK-AMENDMENT 3; the terminal act)

1. Call `seal.seal(receipt_path)` immediately after the receipt file at Step 4.5 has been written to disk.
2. **No covenant-scoped write may happen after this point.** "Covenant-scoped" means anything the receipt measured or should have measured: OS substrate (categories a/b/d), user/studio content (category c), and governance chrome (nav-blocks). Every such write, at every step of this playbook, MUST go through `seal.record_write()` — after `seal()`, any further call raises `PostReceiptWriteError`, full stop.
3. Step 5A/5B's own bookkeeping — updating `.tropo/version.md` to `target_version`, moving the update folder from `pending/` to `applied/`/`failed/`, appending `update-history.jsonl` — happens intentionally AFTER the seal, and is NOT routed through `seal.record_write()`. These are the update's own terminal administrative record of an already-decided outcome; none of them touch content the receipt measures (OS substrate content, user content, or nav chrome), so they cannot retroactively invalidate what the receipt already proved. If a future change ever needs `.tropo/version.md` or the update-history append to influence the covenant hash, that is a design change to the receipt's scope, not a reason to bypass the seal — raise it as a spec question, don't route the write through `record_write()` "just this once."

4. Log: `[update_id] applied — vault now at <target_version>`
