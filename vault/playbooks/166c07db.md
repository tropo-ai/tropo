# Update Walk — Box Flow

*The client half of the v1.94 delivery channel (4e9ce4cc row 5): how a
studio takes an update whose image is the box. The update image is the box
MINUS the customer-identity set; the mandatory vehicle is BOOTSTRAP; the
manifest is fetched, never shipped.*

**Audience:** the concierge (Po) or the studio's operating agent, walking a
customer-owned studio through an update. Every step is a command or a
read — no deliberation over file operations (that era ended with the
lift-and-replace engine, ea09fc6e).

---

## Preconditions

1. `.tropo/update-source.json` exists and names `manifest_url`. (It ships
   in every box since the address cure; a missing file is a defect to
   surface, not a reason to guess a URL.)
2. Network reachable. Offline is a SKIP, not an error — say so and stop.
3. A staging directory OUTSIDE the studio tree (see Step 3 for why this is
   load-bearing).
4. The studio's git tree is clean, or you have the owner's explicit word
   to proceed anyway. An update over uncommitted work muddies every later
   diff.

## Step 1 — Fetch the manifest and derive YOUR view

```bash
python3 - <<'PY'
import json, urllib.request, secrets
src = json.load(open('.tropo/update-source.json'))
url = src['manifest_url'] + '?verify=' + secrets.token_hex(8)   # never a cached copy
manifest = json.load(urllib.request.urlopen(urllib.request.Request(url, headers={'Cache-Control': 'no-cache'}), timeout=30))
open('/tmp/updates-manifest-fetched.json', 'w').write(json.dumps(manifest))
print('current:', manifest.get('current'))
PY
```

The manifest carries the FULL catalog; YOUR view is derived client-side by
comparing `.tropo/version.md` (your version) against it. Exactly one of
three shapes results (port of `render_for_client`, the generator documents
it for this walk):

- **Up to date** — no catalog row is newer than you. Say so; done.
- **`migration_required`** — you are below `minimum_supported`. Follow the
  message's instruction (intermediate installs, in order). Do not improvise
  a skip.
- **ONE pending row (the lift)** — the channel's shape since A4: chained
  and lift end states are identical, so you are offered exactly one entry,
  the newest, whose `min_compatible` is the oldest version the lift span
  covers. **If the row carries no `url`**, the transport for that hop is
  out-of-band (request the image from your steward — the pre-cutover
  1.87–1.93 rows are url-less by design); do NOT treat it as an error in
  your studio.

## Step 2 — HEAD the zip before you commit to anything

```bash
curl -fsI "<the lift row's url>"
```

A url that does not HEAD 200 is a channel defect — report it to the
vendor; do not download around it.

## Step 3 — Download to staging OUTSIDE the studio

```bash
STAGING=$(mktemp -d "${TMPDIR:-/tmp}/tropo-update-XXXXXX")
curl -fL "<url>" -o "$STAGING/tropo-os-v<version>.zip"
unzip -q "$STAGING/tropo-os-v<version>.zip" -d "$STAGING/image"
```

OUTSIDE is load-bearing: downloading or unzipping inside the studio makes
the image's tree part of the studio before any plan exists, and a
run-folder or stash landmine inside the walked tree is exactly the class
that has eaten baselines before (d9025a97). The studio is only ever
touched by the applier, after the plan.

## Step 4 — Plan (writes nothing)

```bash
python3 "$STAGING/image/vault/tools/tropo-apply-image.py" plan \
  --image "$STAGING/image" --studio . \
  --prior-manifest tropo-image-manifest.json
```

READ the output: mode, replace count, delete count, skip count. The
delete-set is honest in mode=full — files the prior manifest had that the
new image does not. Anything in the delete-set you did not expect, stop and
surface it to the owner before Step 5.

## Step 5 — Confirm with the owner

The one human gate in the walk: present the plan's counts and the version
jump, and get the owner's word. This is the update being applied to THEIR
studio.

## Step 6 — Apply via BOOTSTRAP (mandatory)

```bash
python3 "$STAGING/image/vault/tools/tropo-apply-image.py" bootstrap \
  --image "$STAGING/image" --studio . \
  --prior-manifest tropo-image-manifest.json \
  > /tmp/apply-receipt.json
```

BOOTSTRAP, never the installed applier directly: bootstrap stages and runs
the NEW image's own applier, so a studio on retired semantics still
receives new semantics, and the migration contract is asserted before
anything writes. Backup happens BEFORE the first write; failure halts with
the operation named and NO rollback (the backup and the applied prefix are
the evidence — see ea09fc6e AC8).

## Step 7 — Rebuild (load-bearing, not cosmetic)

A real apply leaves the derived navigation empty and replaced entries
unindexed (measured: 198 of 221 nav skips, 945 entries unindexed — A5).
The rebuild is the walk's step, not an optional cleanup. The command
depends on which customer you are:

**Fresh-box studio (no git — the zip shape):**

```bash
python3 vault/tools/tropo-rebuild-index.py --apply
```

No prior machine-local floor evidence exists, so the box's own shipped
index is the only floor and the rebuild derives to match it.

**Upgrading studio with git:** land the apply FIRST, then reconcile —

```bash
git add -A && git commit -m "apply tropo-os v<version> (box walk)"
python3 vault/tools/tropo-rebuild-index.py --apply --reconcile
```

The apply just rewrote the index surfaces wholesale, so your studio's
shrink-floor evidence legitimately mismatches (a plain rebuild refuses
with `stale-surface-mismatch`), and reconcile treats uncommitted inputs
as non-authoritative (it refuses with `land, revert, or isolate` until
you commit). Land, then reconcile — both refusals are the tool naming
their own remedies; follow them rather than working around them.

## Step 8 — Verify receipt and history row

```bash
python3 - <<'PY'
import json
receipt = json.load(open('/tmp/apply-receipt.json'))
assert receipt['schema'] == 'tropo.apply-receipt/v1', receipt
row = json.loads(open('vault/updates/update-history.jsonl').readlines()[-1])
print('receipt version:', receipt['version'], '| history row:', row['version'], row['outcome'])
PY
```

The receipt is ONE JSON document (bootstrap parsed exactly that). The
history file grows by exactly one row per apply — success or failure — and
your prior rows must still be there as an untouched prefix. If either half
is wrong, that is a defect to report, not a condition to quietly fix.

---

## What this walk deliberately never does

- **Never hand-merges files.** The engine plans; you read and confirm.
- **Never writes the manifest into the studio.** The box carries none (A7);
  your version truth is `.tropo/version.md` plus the fetched manifest.
- **Never applies over the identity set.** STUDIO.md,
  operating-agreement.md, CLAUDE.md, AGENTS.md (root) are excluded at the
  apply surface — a planted customer edit survives byte-identical (A1, the
  regression this whole channel exists to never repeat).
- **Never treats an old client's halt as retriable.** A pre-v1.94 playbook
  halting on a box-shaped artifact means the SEQUENCING was wrong (the
  client must upgrade before the manifest advertises boxes) — escalate,
  don't retry.
