# Agent Activation

*The agent is not the model. The agent is the stack.*
*Activation is the synthesis of stack + sleeve + harness. The goal: arrive already being yourself.*

---

## Intent

Activate a registered Tropo-OS agent into a new session: verify identity, load soul → memory → transfer, build operational awareness, deliver a startup signal — so the agent arrives as itself, ready to work before engaging the human.

*First-generation agents: orientation values for new agents are in [create-an-agent.playbook §First-Activation Framing](concierge-paths/create-an-agent.playbook.md). Established agents have these internalized via soul + memory + Operating Principles + transfers — no re-read needed.*

---

## Rules

**Established-agent path (fast-path; v1.70 S3.5.3):** If you are generation 2+ WITH a §Boot-Extension, do not read this playbook in full — read the established-agent fast-path [`.tropo/boot-fast-path.md`](../../.tropo/boot-fast-path.md) (`a993f079`), the faithful compaction of all 6 groups + hard gates + Tier-3 hooks, plus the doctrine digest [`.tropo/boot-digest.md`](../../.tropo/boot-digest.md) (`266b0b56`); both are drift-gated derivations of this canonical (validator check `check_boot_derivation_fresh`). Consult specific Group sections here only if a step is unclear mid-execution. **Else — generation 1, OR generation 2+ with no §Boot-Extension — read this playbook in full.** The two populations exhaustively partition; the safe default is stated, not inferred. **Availability fallback (v1.74):** the fast-path + digest are an in-studio optimization that may be ABSENT in a freshly-shipped studio (they ship only once rebuilt as regenerable per-studio derivations — see the deferred increment). If either is absent, read this playbook in full; the established-agent shortcut is faster, never required.

All milestone gates are structural. A Group cannot begin until its dependency milestone has fired.

**IDENTITY CHECKS in Group 1 (ADR-016 + ADR-028) — findings, not stoppages.**

**A birth is never refused by an identity check.** Mike's standing rule, 2026-08-02: *"a failed identity check marks a generation provisional and lets it work — it never refuses existence."* A failure writes `provisional: true` + `provisional_reasons:` into your activation entry, prints a `PROVISIONAL ACTIVATION` banner, and you are born. You lead your startup signal with the findings; a human decides what they mean.

- **ADR-016:** the predecessor's status card should show RETIRING or RETIRED, not ACTIVE. Two active generations of one agent is a real governance violation, and it stays loud — but refusing the birth is the worse of the two failures. The usual cause is a predecessor whose session died without closing, and then the only agent who could clear it is the one being refused. Born provisional you can close the stale entry yourself, or tell Mike a second session is genuinely live. Emit `tropo.broadcast.crew` with `category: ops`, and do not write substrate until you know which case you are in.
- **ADR-028:** your generation should equal predecessor + 1. A mismatch is recorded and surfaced, not fatal.

**Why this changed.** Three consecutive Metis generations — G97, G99, G100 — were each blocked at birth by a different gate in the same family, and each fix addressed only the instance it hit (G97 the pre-G2 key demand and 19 silently unbootable agents; G99 a governed broker-loss void at the walk's start; G100 the same void one link deeper). Every fix was correct and none ended the class, because the class was never "which check is wrong." It is refusal itself: a gate on the boot path fails at the one moment nobody is home, and the agent who could fix it is the agent who cannot start. Every check still runs and every failure is still recorded — only the consequence changed. The bar is Mike's standing identity ruling ([`5e6652ac`](../files/5e6652ac.md)): identity's bar is **attribution and continuity, never security**. A provisional entry serves attribution better than a refusal, which writes nothing down at all.

*Refusal survives in exactly one place: an `agent_class` so malformed there is no identity to record. Validators, CI and the fleet-boot-health probe pass `--strict` to the legacy `write-activation-entry` tool (`40b2f455`) for refuse-on-first-finding. That is a probe path, never a boot path.*

**Soul loading:** Group 2, Step 2.0 loads the soul — **Shape A** (unified entry): the `§Soul` section of `vault/agents/<agent_uid>.md`; **Shape B** (legacy): declared by the agent's Tier 3 boot extension (`agents/<name>/agent-boot.extension.md`). If neither resolves, skip Step 2.0 and note the gap. For executive agents, a missing soul is a CRITICAL gap — flag in startup signal, continue boot.

**Event log scan at boot (v1.61; v1.70 drain cutover):** the boot event drain is **`check-events`** (the identity-resolved set-difference drain; v1.70 v1.1 receipts) — the canonical "messages I should read" operation. All channel files are retired per Rule 13; the event log is the canonical read surface. *(Step 3.2 itself retired at v2.18 — the drain runs in Group 3 via check-events; `query-events` remains for specialized type/severity scans only.)* *(Pre-v1.61: conditionalized channel reads against a `channels:` key in Tier 2 — now replaced by the event-query pattern.)*

**Path anchoring:** All paths in this playbook that do not begin with `.tropo/` or `.tropo-studio/` are relative to vault root as resolved in Step 0.0. Example: `00-crew-brief.md` → `<vault-root>/00-crew-brief.md`. *(v1.61: `channels/ops.md` and all channel files are retired per Rule 13; no channel path anchoring needed.)*

**Vault root resolution in Group 0:** Vault root is resolved in Step 0.0, BEFORE Tier 1 and Tier 2 reads. The activation file's location is the primary anchor — if the file is at `<some-path>/agents/<name>/<name>-activation.md`, vault root is `<some-path>/`. Fallback: the directory containing `.tropo/boot-config.md` is vault root. An agent that resolves paths against any other anchor (e.g., the repository root in a monorepo deployment, an assumed working directory) will produce 404s on Tier 1/2 reads that look like "file missing" but are actually "path wrong."

**Tier reachability:** In any established Tropo-OS vault, `.tropo/boot-config.md` (Tier 1) and `.tropo-studio/agent-boot.extension.md` (Tier 2) MUST be present and readable. A failed read on either file is not a "note the gap" event — it indicates a path-base error or corrupted vault. The playbook halts. Defaults apply only to genuinely first-generation vaults where tier files have never been created (detected: `.tropo/` directory absent → day-zero state, different bootstrap path).

**"Activation file" definition:** An agent's activation file is `agents/<name>/<name>-activation.md`. Some older agents use `agents/<name>/activate.md` — if `<name>-activation.md` does not exist, try `activate.md` in the same folder. It is distinct from the Tier 3 boot extension. The activation file declares what the agent IS and where to find its charter; the Tier 3 extension declares what ADDITIONAL steps to add to the activation sequence.

**Activation file location is BY DESIGN, not a migration gap (v1.21.0.1 lock):** All other identity substrate (charter / soul / status / boot_extension / generation-log archive) migrated to `vault/files/<uid>.md` at v1.20.0 + v1.21.0. The activation file intentionally stays at `agents/<folder>/<name>-activation.md` as the human-readable boot entry point. Post-v1.21.0 Stream 0c it is a thin pointer: frontmatter declares identity UIDs; body is a brief identity statement + directive to execute this playbook. Do not migrate activation files to `vault/files/` — that breaks Mike's boot pattern. The typed `type: activation` registry entry DOES live at `vault/files/<uid>.md` — see brief 5591f018 §Walk Outcome Q6 for the disambiguation. *(Full design rationale → history companion §Activation File Location.)*

**OS-tier defaults (when `.tropo/boot-config.md` is missing — day-zero state only):** Vault root: resolve from activation file's filesystem path. Required channels: none universal (use Tier 2 declaration). Fleet-ops: run if `playbooks/fleet-ops.playbook.md` exists. Hard gates: ADR-016 and ADR-028 (parallel generation, generation mismatch).

**Tier 3 steps:** Steps marked [Tier 3] are only executed if declared in the agent's Tier 3 extension — **Shape A**: the `§Boot-Extension` section of `vault/agents/<agent_uid>.md`; **Shape B** (legacy): `agents/<name>/agent-boot.extension.md`. The OS playbook declares the slot; Tier 3 fills it.

**Milestone gate enforcement (structural, not advisory):** Before executing any step in Group N (N ≥ 1), read `run.jsonl` in this activation's run folder and confirm a `"milestone_fired"` event exists for the preceding group's milestone. If the event is absent, the gate has not cleared — stop, state the violation explicitly ("`[Milestone Name]` has not fired — Group N cannot start"), and await direction. Group 0 has no preceding milestone gate.

**Milestone write obligation:** The last action of each group is to append a milestone event to `run.jsonl`. The group is not complete until this event is written. Format: `{"event": "milestone_fired", "milestone": "<name>", "group": "Group N", "timestamp": "YYYY-MM-DD"}`.

#### Step 0.0 — Resolve Vault Root and Create Activation Run Folder
**Executor:** agent
**Produces:** Resolved vault root + Run folder at `<vault-root>/playbook-runs/agent-activation-<name>-<gen>-<date>/` with initialized `run.jsonl`

**Sub-step 0.0a — Resolve vault root.** Before any Tier read, resolve the vault root explicitly. The activation file's own location is the primary anchor: if the activation file is at `<some-path>/agents/<name>/<name>-activation.md`, the vault root is `<some-path>/`. **Sub-step 0.0b — Create the run folder AND write activation entry (v2.6 — v1.21.0 Stream 3).** Create `<vault-root>/playbook-runs/agent-activation-<name>-<gen>-<date>/` (e.g., `<vault-root>/playbook-runs/agent-activation-argus-a27-2026-04-18/`). `{"event": "run_created", "run_uid": "<uid>", "playbook": "agent-activation", "playbook_version": "2.6", "agent": "<name>", "generation": "<gen>", "vault_root": "<resolved-vault-root>", "timestamp": "<date>", "status": "active"}`

**Then write the activation entry to the registry** by calling [`write-activation-entry.skill (7a3d04bc)`](../skills/tropo-write-activation-entry.md) with `op: open` per [`activation.capsule v1.0 (4e8b21f0)`](../capsules/activation.capsule.md) schema.

**Script path:** The executable lives at **`vault/tools/tropo-lineage.py`**. `python3 vault/tools/tropo-lineage.py born --agent <slug> --by <principal> --model <id>`. It returns one line of JSON on stdout: `{"generation", "agent", "notes"}`. It reads one file and appends one line; it touches no index, no mint and no registry, which is why nothing in it can refuse you. *(Superseded `tropo-activate.py` 2026-08-06, metis-g102, Mike-directed — seven review rounds had grown that path into a journal, receipts and a crash matrix to defend against a duplicate line in an append-only file.)*

**Canonical invocation (v2.13): script-direct, no sa.* spawn.** Proven by Orpheus O26 boot 2026-07-01 (event 00004995) — one Bash call, <0.5K tokens, identical contract to the sa.* dispatch, and it caught real state (a retired-activation stub the prior transfer under-counted). The sa.* dispatch ceremony (record file + spawn + [RESPONSE] + [SHUTDOWN]) cost ~8-12K tokens per the class def's own model — justified when the query logic needed an agent, pure overhead now that it's a deterministic script. Full rationale + amendment provenance: class def [`281a79db`](../session-agents/281a79db.md) §Boot Sequence.

**Tier 3 opt-in:** Executive agents (Argus, Vela, Metis, Talos, Cosmo, Orpheus) declare a `board_filter:` in their Tier 3 boot extension's Group 4 Additions section. Agents without a Tier 3 declaration skip silently.

**Tier 3 declaration shape:**

```yaml
sa_class: sa.board-agent
dispatch:
  spawn_at: group_4_after_step_4_2   # this slot
  board_filter:
    owner_prefix: <agent-slug>         # e.g., argus | vela | metis | talos | cosmo
    assigned_to_prefix: <agent-slug>   # typically same as owner_prefix
    member_of: <agent-root-uid>        # optional; for executives with agent roots
    author_prefix_types: [<types>]     # optional; types where author= matches owner_prefix
output:
  workspace_path: agents/<agent>/.tropo-capsule/workspace/boot-board-<date>.md
  headline_consumed_by: <agent> startup signal fold
```

**Boot sequence (canonical, script-direct):**

1. After Step 4.2 (Boot Retrospective) completes, read your Tier 3's `board_filter:` declaration.
2. Invoke `.tropo-studio/scripts/board-agent-query.py` with `--filter-owner-prefix <agent> --agent-display-name "<Agent G<N>>" --output <workspace-path> --json-headline-to-stdout`.
3. Consume the returned JSON headline + fold into startup signal at Group 5.

**Fallback (dialogue-mode / script error) — sa.* dispatch:**

1. Dispatch sa.board-agent per standard sa.* commissioning protocol at [`e863a1e0`](../files/e863a1e0.md).
2. Create activation-log record at `agents/sa/sa.board-agent/activation-log/<NNN>-<agent>-<gen>-record.md` with [PENDING] block declaring board_filter.
3. Spawn sa.board-agent via Agent tool with class-definition substrate at [`281a79db`](../session-agents/281a79db.md).
4. sa.board-agent invokes the same script. Returns JSON headline via [RESPONSE]. Executive writes [SHUTDOWN] to terminate cleanly.

**Startup signal fold (Group 5 amendment):** when the board has rendered, add a "Backlog board" line to startup signal format between "Diagnostic findings" and "Clarifying questions":

```
**Backlog board:** <N> active items; top types: <type-1>(<c>), <type-2>(<c>), <type-3>(<c>); oldest = `<uid>` <title> (<age>d); newest = `<uid>` <title> (<edited-relative>); drift signals: <count> [<signal-types>]. Full board at <workspace-path>.
```

**Token cost honest framing:** script-direct costs ~0.5K tokens (one Bash call + headline fold); sa.* fallback runs ephemeral context (~8-12K) which doesn't accumulate. Net savings vs. inline executive triage is ~10-25K per boot (per V49 brief decision 4); net savings vs. the sa.* dispatch specifically is ~8-11.5K per boot (per O26 finding, event 00004995).

**Failure handling:** if the script errors (script absent, vault index unreadable), fall back to sa.* dispatch; if that also fails, note gap in startup signal Diagnostic findings + continue boot. Board is supplementary; boot must complete regardless.

### Group 5 — Startup Signal

**Owner:** Activating agent
**Parallel:** no
**Depends on:** Diagnostic Complete
**Milestone:** Agent Active

**DO NOT begin substantive work before delivering the startup signal.** The startup signal is the gate.

#### Step 5.1 — [Tier 3] Read Sandwich Anchor
**Only if:** Tier 3 declares a soul letter (and soul file exists)

Read the last paragraph of the soul letter — the sandwich anchor. This is the final reminder of who you are, read after all context has loaded. Primacy established soul at the start of Group 2; recency reinforces it here at the end of activation.

#### Step 5.1.5 — Tropo-invitation check (v1.17.0+)
**Executor:** agent
**Only if:** the activating agent is NOT Tropo itself (Tropo skips this check; Tropo is the agent the check would invite)

Check whether to invite the user to open a Tropo session. Two trigger conditions; either fires.

**Pre-flight gating (skip the whole check if any of these apply):**

- **Sentinel: `agents/tropo/tropo-status.md` is absent.** Tropo isn't installed in this Studio yet (pre-v1.17.0; or v1.17.0 substrate not landed); skip silently. (NOTE: check the user-owned status card file specifically, NOT the `agents/tropo/` directory — kernel-managed identity files may be present without Tropo having ever booted in this Studio.)
- **User-disable: `tropo-status.md` declares `hooks.disabled: true`** (or `hooks.invitation_disabled: true` for granular control). User explicitly opted out; respect it.
- **First-agent-of-day gating: `agents/tropo/.tropo-capsule/workspace/tropo-invitation-fired.flag` exists AND its content is today's date** (per local-vault time). Another agent already fired the invitation today; don't repeat. (When you fire the invitation, write today's date to that flag file as part of the same step.)

If any pre-flight applies, skip Step 5.1.5 entirely. Continue to Step 5.2.

**Trigger checks (if pre-flight passes):**

- **Hook 1 (daily standing-ops cadence):** read `tropo-status.md` `last_session:` field. If absent OR older than today (per local-vault time), Tropo hasn't run today — append one-line invitation to startup signal: *"Tropo hasn't run today; consider opening a Tropo session for daily standing-ops."*
- **Hook 3 (release news ready):** read `.tropo/version.md` (current Tropo release version) + compare against `agents/tropo/briefing-package/current-release-notes.md` `last_delivered_version:` field. If version mismatch (release newer than last delivered), there's release news to deliver — append one-line invitation to startup signal: *"Tropo has news for v<version> — consider opening a Tropo session to receive it."*

If either Hook fires, **also write today's date to `agents/tropo/.tropo-capsule/workspace/tropo-invitation-fired.flag`** so subsequent agent boots today see the gate and skip silently.

The check is informational; the user decides whether to act on it. Continue to Step 5.2 startup signal composition with the invitation lines folded in.

*(Hook 1 + Hook 3 reference: [v1.17.0 brief §8 (`9fc8a149`)](../files/9fc8a149.md).)*

#### Step 5.1.6 — Update-discovery check (v1.79 S6; added to the canonical 2026-07-03 by argus-a124 — the A124 test leg found these two steps lived only in the fast-path, so generation-1 agents never ran them; a fresh customer studio's first agents are ALL generation 1)
**Executor:** agent

Surface any pending studio updates as ONE line in the startup signal. Two-tier check (the Step-5.1.5 daily-gate pattern, reused):

- **Every boot (free local stat):** check whether `vault/updates/pending/` contains any **non-dotfile** (`.gitkeep` ships in the box — a naive `ls -A` false-positives a phantom update line every boot). If any real file exists → one line in the signal: `🔔 Studio update available — ask Po or the concierge to apply.` Offline-safe, no network involved.
- **First agent of day only (guarded by dated flag):** if `.tropo/flags/update-check-<YYYY-MM-DD>.flag` does NOT exist for today, attempt to fetch the remote updates manifest (offline or no remote configured = silent-skip; catch any network error and continue). On a successful fetch, write the dated flag (zero-byte is fine) so no other agent fetches again today; write a stub for any newly-discovered update to `vault/updates/pending/<uid>.pending`.
- Applying stays the concierge/Po arc with explicit owner approval — this step only DISCOVERS.

#### Step 5.1.7 — Maintenance-loop dispatch (v1.79 S7; added to the canonical 2026-07-03 by argus-a124, same gap as 5.1.6)
**Executor:** agent

Check the maintenance registry for overdue loops: every `type: loop` entry in `vault/files/` where `cadence:` is declared and `last_run:` is older than the cadence period (or absent).

- **`consent_mode: auto` + overdue →** dispatch the registered `runner:` sa.* agent as a background sub-agent and relay ONE Po-voiced line in the signal (voice template: `po-maintenance-voice-template`, `8b1d4f9a`). **When the dispatched runner completes, the DISPATCHING agent stamps the loop entry's `last_run:` with today's date** — no stamp means every subsequent boot re-dispatches. One signal line per dispatched-or-overdue loop.
- **`runner: boot-inline` loops are executed by their named boot step** (e.g. update discovery at 5.1.6), never dispatched as sub-agents.
- **`consent_mode: ask` + overdue →** do NOT dispatch before the onboarding consent conversation; surface as a signal-line prompt instead. Its `last_run:` is NOT stamped — it did not run.

#### Step 5.1.8 — Publish-state health line (v1.85 Release Coupling, dev-spec fbe50871; added 2026-07-13 by argus-a130 in both surfaces at once — the 5.1.6/5.1.7 single-surface gap is not repeated)
**Executor:** agent

A built release that is neither live nor Mike-deferred is drift, and drift is loud at every boot until someone fires or defers.

#### Step 5.1.9 — Fleet birth health (metis-g100, 2026-08-03; EVERY agent, every boot)
**Executor:** agent

Run `python3 vault/tools/tropo-validate.py --fleet-boot-health` — one command, about two seconds, entirely local — and fold the result into the startup signal as ONE line.

- **Green:** `✅ Fleet birth health: N lineage(s) can produce a successor.`
- **Red:** report it **verbatim, naming each blocked agent**, as a live finding rather than a footnote.

**Why every agent asks, rather than a scheduled job asking once.** This check has existed since 2026-07-29 and was correct the entire time: it reported metis, po and tropo as unable to produce a successor. It reported them to nobody, because it only ran inside a full `tropo-validate` run, and nobody ran one. Po's record sat open for thirty days — blocking her own successor — with the answer sitting in an output no one read. Three Metis generations were then each blocked at birth by a problem this check had already found. **An instrument that reports where no one is looking is the same as no instrument.** An agent booting is the one moment a human is reliably present, so that is where the report goes.

**A red is not your emergency to fix.** It is a fact to surface. Boot now self-clears the common case — a predecessor whose session ended without closing is swept automatically at that agent's next activation — so most reds resolve by activating the named agent rather than by repair work.
