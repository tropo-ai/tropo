# Names for humans, UIDs for records — the entity-reference rule

**Mike, verbatim (2026-08-30, at the W2 walk):** *"I don't want a huge migration. I want to
look forward and want to establish rules for new studios. I'm just thinking that UID is
important when referencing entities. Humans will never talk UID, I will say 'tell Argus to
do X' I think in all our logs and sources of record, we should always record an entity UID:
agents, vaults, files, etc."* (Preceding turn, same walk: *"It's fine for discussion, but a
UID should always be referenced, I think."*)

## The rule

1. **Humans speak names; the system records UIDs.** "Tell Argus to do X" is the human
   layer. The record of that act carries `cdf9b3ad`. Translation between the two is the
   machine's job, never the human's.
2. **Every log and source of record carries the entity UID for every entity it
   references** — agents (party UID), principals (principal UID), studios (entity record
   uid), governed files (file UID). A record that names an entity only by display name is
   under-specified by construction.
3. **A resolved label may ride beside the UID** wherever humans also read the surface (the
   `actor` + `actor_label_resolved` two-field pattern in the release journal is the house
   form). The label is a convenience; the UID is the reference. Readers resolve identity by
   UID against the registry, never by parsing a label.
4. **Forward-binding, never retroactive.** The rule binds new schemas, new record types,
   new log surfaces, and every new studio from its first record. Existing argo-os substrate
   (frontmatter slugs, historical journals) is grandfathered as-is: no migration, no bulk
   sweep. Where an old surface is being amended anyway for another reason, adopting the
   two-field pattern is welcome; it is never itself a work item.
5. **Frontmatter boundary (release-owner reading, open to Mike's override):** governed-file
   frontmatter (`owner`, `author`, `created_by`) keeps the slug convention — those fields
   are read by humans in diffs constantly and resolve through the registry. The rule's
   teeth are in LOGS and machine-derived records: journals, event streams, run records,
   scorecards, registries, telemetry.

## Why (the strategic ground)

Names drift, collide, and localize; UIDs do not. A journal that records `"actor": "mike"`
cannot distinguish a human from a machine forging a label (the release journal did exactly
this — every row ever written was undecidable until the W2 fold). A multi-studio org has
many Argus lines; `cdf9b3ad` has exactly one referent. Same logic the composite-filename
ruling locked: *"Human readable, grep-able, federation ready"* — names for humans, UIDs for
machines, both present where both audiences read.

## Enforcement instances (live now)

- **Release engine (3d8d4351, W2):** `actor` carries the principal UID, never a display
  name; `actor_label_resolved` carries the name; the forged-label writer is cured.
- **Event bus:** subjects already carry party UIDs (house practice, now doctrine).
- **Studio manifest (identity ruling):** entity name + entity record uid + mint_prefix.
- **Studio-ops v2.0 (Vela, in design):** the shared log's `by` field binds to this rule —
  routed 2026-08-30.
- **B-8 companions:** charters name crew by party UID; a new studio's records are born
  compliant — nothing to migrate because nothing pre-dates the rule there.
