**Why Talos is step_owner_role:** the execution layer is engineering. Subprocess orchestration, DSL grammar evaluation, validator extension dispatch, sa.* commissioning wiring, result aggregation into run.jsonl event types — all engineering implementation work. Vela owns the overall pipeline + the dispatch shape (which verification_methods need what), Talos owns the actual runtime.

**What it does (per verification_method):**

| verification_method | Runtime action | Result capture |
|---|---|---|
| `machine_executable_script` | subprocess.run(command_line); capture exit_code, stdout, stderr | test_executed event: pass = exit 0, fail = exit non-zero; stdout/stderr tail (last 50 lines) for diagnostic |
| `deterministic_assertion` | Engine DSL evaluator parses expression per pipeline.capsule v3.0 §6; evaluates against current substrate state | test_executed event: pass = expression true, fail = expression false; expression-tree-result for diagnostic |
| `structural_check` | Engine invokes named validator extension function in tropo-validate.py | test_executed event: pass = check returns clean, fail = check returns violations; violations list for diagnostic |
| `agentic_review` | Engine dispatches sa.* class per dispatch_target via standard commissioning protocol [e863a1e0]; awaits [RESPONSE] block in activation-log record | test_executed event: pass/fail per sa.* verdict in [RESPONSE]; sa.* findings list for diagnostic |
| `manual_walk` | Engine surfaces Mike walk prompt; Vela orchestrates Mike's walk session; captures Mike's pass/fail verdict + rationale | test_executed event: pass/fail per Mike verdict; rationale ≥50 chars |

**Aggregation:** after all behaviors executed, engine writes test_aggregate event to run.jsonl with summary (pass_count, fail_count, per-behavior verdicts, total runtime). Aggregate becomes step 4 validate-coverage's input.

**Failure semantics:** individual behavior failures don't halt step execution — all behaviors execute; aggregate captures the full pass/fail picture. Step 4 validate-coverage decides whether aggregate satisfies coverage requirements.

**Hands off to:** step 4 validate-coverage.

## verification_command fix (Vela V64, 2026-07-09, 974b08ad)

The step's `verification_command` had been `npm test` in `/Users/mike/dev/tropo-ai` since original v1.0 authoring — a different repository, not this studio. Never caught before because no real test-pipeline activation had actually driven this step to execution until the v1.84.1 federation close-out. Fixed to a harmless no-op (`python3 -c "pass"`, `verdict_cwd: .`) — this field only needs to be truthy to unlock the engine's real per-behavior aggregate path; it is not itself the verdict source. See `verification_command_note` in frontmatter.

**Separately, a real engine gap this exposed (Talos's lane, routed, not fixed here):** the pipeline-run that hit this had its `05d9ecc5` step declared via the engine's "B1 auto-heal" path (`9e7003b1.py`, step-data dict construction ~L1489-1502) rather than the normal declaration path — and that auto-heal dict construction does not copy `verification_command`/`verdict_cwd` from the current step definition at all, unlike the normal path (same file, ~L1073-1080) which does. Any step that gets auto-healed into an in-flight run silently loses these two fields regardless of what's declared on disk. This is the actual blocking bug for the v1.84.1 close-out (not the wrong command value above, which is cosmetic/wasteful but not blocking since the aggregate check only reads the behaviors_covered-derived `fail_count`, not this command's own exit code) — flagged to Talos to fix in the engine.

## DSL rewrite note (Talos, 2026-07-04, 4f87d056/0fa72100)

The original 8-item prose `exit_criteria` list (`each behaviors_covered entry executed exactly once...` + one descriptive line per `verification_method`) did not parse (`parse_exit_criterion` — "unrecognized criterion shape" on every line) and, per-`verification_method` items describe a CONDITIONAL per-run shape (most runs exercise only a subset of the five methods) that the DSL has no per-event-type dispatch for. Consolidated into the ONE criterion the grammar's `aggregate:` dispatch (added since the v1.62 dogfood, `062c5544`) can genuinely check against the real `test_aggregate` event fields this step's own runtime code emits (`pass_count`/`fail_count`/`total`/`verdict`/`behaviors` — see `action_step_complete` ~L1576-1594 in `9e7003b1.py`; NOT `behaviors_executed`/`behaviors_covered_count`, which Argus's first-pass candidate used and which do not exist in the emitted event). The five per-method descriptive lines remain accurate as documentation — they are the table above, verbatim — so nothing is lost, only de-duplicated out of the machine-evaluated frontmatter list.
