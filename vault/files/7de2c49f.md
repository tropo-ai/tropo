# release-freeze-verified-package — the commit point for candidate identity

<!-- nav-block:start -->
**📍 Vault Path:** [tropo-subsystems](aae9a37b.md) → [Tropo Playbooks](76bab75f.md) → **release-freeze-verified-package — release-pipeline step**
<!-- nav-block:end -->

## Purpose

Turn a candidate into a frozen package, once, on evidence that is bound to the
exact bytes being frozen.

The order matters and it is the reason this node exists. Before dev-spec
[2fae6312](2fae6312.md), the four instruments in the Verify stage produced
receipts against a package that was already declared frozen, which made the
freeze an assertion the evidence arrived after. Here the candidate is built and
the instruments run against it while it is still a candidate; this step then
re-hashes those bytes, proves the four receipts belong to them, and only then
emits the freeze.

A freeze that precedes its own evidence is a claim. A freeze that follows it is
a fact.

## Structure

Leaf step. No children. Fourth-and-a-half position in Verify: it follows the
four declared instruments and hands to Publish.

    4262d5fa -> a0f2bea8 -> bc6b17ec -> c6b61fb9 -> 7de2c49f -> 8e03f8d6
    validator   harness     external    cold walk   FREEZE      publish

## Nodes

No child nodes. This is a leaf WorkflowNode.

## Flow Rules

**Completes when** all four exit criteria hold:

1. **The bytes are the same bytes.** The candidate zip is re-hashed and must
   equal the `candidate_sha256` recorded at build. This is not a formality: the
   instruments ran earlier, and anything that touched the artifact between then
   and now silently detaches every receipt from the thing being shipped.
2. **The evidence is exactly four receipts, and they are these bytes' receipts.**
   One passing receipt per declared instrument — full-release-validation
   (`4262d5fa`), release-harness-gate (`a0f2bea8`), external-test (`bc6b17ec`),
   cold-boot-walk (`c6b61fb9`) — each bound by
   `(run_uid, candidate_sha256, instrument)`. Four receipts that do not name
   this candidate are four receipts for something else. Three passing receipts
   and one absent is a fail, not a rounding error.
3. **No invalidation is live.** A byte change before freeze emits
   `tropo.release.candidate_invalidated`, which invalidates the prior receipts.
   A candidate carrying a live invalidation cannot be frozen; it must be rebuilt
   and re-verified.
4. **The freeze is singular.** Exactly one active
   `tropo.release.package_frozen` exists for the run afterwards, and none
   existed before. This node emits the only active one.

**Advances to:** publish (`8e03f8d6`) on pass.

**On fail:** the run pauses here. Nothing outward has happened yet, which is the
point of placing the step before Publish rather than inside it — this is the
last boundary at which stopping costs nothing.

## Event Vocabulary

| Event | When | Cardinality |
|---|---|---|
| `tropo.release.candidate_built` | build produces candidate bytes | one active candidate per run |
| `tropo.release.candidate_invalidated` | bytes change before freeze; prior receipts are invalidated | any number, sequentially |
| `tropo.release.package_frozen` | this step, on all four criteria | exactly one active per run |
| `tropo.release.package_superseded` | reserved: replacement of an ALREADY-frozen package | never emitted for a mere candidate change |

`candidate_invalidated` and `package_superseded` are deliberately different
events. Collapsing them would make "the candidate changed while we were looking
at it" indistinguishable from "a shipped package was replaced", and only the
second is a public fact.

## Verification Data Contract

The step is machine-verifiable — a re-hash and a receipt count admit no
judgement — so it fires `verify-step` with structured JSON on stdin, in the same
shape the cold-boot-walk uses:

```bash
echo '<json-payload>' | python3 vault/tools/9e7003b1.py \
  --activation-uid <activation-uid> --actor talos-t<N> \
  verify-step 7de2c49f --verification-data-stdin
```

```json
{
  "verdict": "pass" | "fail",
  "verifier_role_resolved": "talos",
  "run_uid": "<pipeline-run-uid>",
  "candidate_sha256": "<hash recorded at build>",
  "rehashed_sha256": "<hash computed now>",
  "instrument_receipts": {
    "4262d5fa": {"receipt_uid": "<uid>", "verdict": "pass", "bound_sha256": "<hash>"},
    "a0f2bea8": {"receipt_uid": "<uid>", "verdict": "pass", "bound_sha256": "<hash>"},
    "bc6b17ec": {"receipt_uid": "<uid>", "verdict": "pass", "bound_sha256": "<hash>"},
    "c6b61fb9": {"receipt_uid": "<uid>", "verdict": "pass", "bound_sha256": "<hash>"}
  },
  "live_invalidations": [],
  "frozen_event_uid": "<uid of the package_frozen this step emitted>",
  "rationale": "<one line>"
}
```

Every `bound_sha256` must equal `rehashed_sha256`, which must equal
`candidate_sha256`. A payload where those three disagree is a fail regardless of
the `verdict` field it carries — the numbers are the verdict, and the field is
only a claim about them.

## Cold-Boot Walk-Through

A stranger following one run through this step, with no other context.

The run arrives here having just passed the cold walk. Somewhere upstream, a
build produced a zip and recorded its hash — call it `abc123` — and emitted
`tropo.release.candidate_built`. Four instruments then ran, each writing a
receipt that names `abc123` alongside the run and the instrument.

This step opens the zip that is on disk right now and hashes it. Suppose it
still hashes to `abc123`. It then looks for receipts naming
`(this run, abc123, <instrument>)` and finds four, one per declared instrument,
all passing. It looks for a live `candidate_invalidated` for this candidate and
finds none. It looks for an existing active `package_frozen` for this run and
finds none. All four criteria hold, so it emits exactly one
`tropo.release.package_frozen` and hands to Publish, which is now eligible for
the first time.

Now suppose instead that someone corrected a typo in the changelog and rebuilt
after the harness ran. The zip on disk hashes to `def456`. The re-hash
disagrees with `abc123` on the first criterion and the step fails without
reaching the others. Nothing outward has happened; the cure is to rebuild the
candidate, let the four instruments run against `def456`, and return here. The
receipts naming `abc123` are not reusable, and that is the entire point — they
describe bytes that are no longer the ones being shipped.

The failure mode this ordering removes is subtle and was live before v1.89: the
old chain let Publish depend directly on the cold walk, so a package could be
verified, quietly altered, and then published, with four passing receipts
sitting in the run describing something else.
