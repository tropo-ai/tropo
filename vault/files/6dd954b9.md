# Memory reinforcement scoring — a recurrence counter for the curator

**📍 Vault Path:** [tropo-subsystems](aae9a37b.md) → [Tropo Work](2d083137.md) → [01-inbox](0a1a36fe.md) → **Memory reinforcement scoring — a recurrence counter for t...**
<!-- nav-block:end -->

*Mike-originated idea (2026-07-20), analyzed + captured by Argus A136 for the v3.1 memory cycle. Routed to the dev-pipeline inbox (`0a1a36fe`). Not yet specced — this brief informs a future dev-spec.*

## The problem

The memory system today scores three signals ([score-formula-doctrine `5f2c1b94`](5f2c1b94.md)): **recency**, **usage** (`reference_count` = how often an entry is *read/cited*, Reddit-Hot log-compressed), and **explicit pins** (Wilson-weighted). The [`sa.memory-curator` (`50c0bdce`)](50c0bdce.md) already has a `MERGE` action — it detects "potential duplicate (similar context + body)" and consolidates into the survivor with the higher `reference_count`, human-ratified.

**What's missing is recurrence.** When the curator merges, it keeps the higher-read entry and drops the other — it does **not** record that the lesson *re-emerged*. So the system tracks how often a memory is *looked up*, but not how often reality *re-taught* it. Those are different, and recurrence is arguably the strongest importance signal:

- read-count → "we look this up a lot" (may just be a handy reference fact).
- pin → "someone flagged it once."
- **recurrence → "the agent independently re-derived this same lesson from fresh experience N separate times."** That is the loudest "this is load-bearing."

Lived proof: Argus's #1 memory pin ("verify by running / against raw") is ten generations (A115–A135) each independently re-learning the same lesson, hand-merged into one entry. That "reality taught us this 10 times" signal exists today only as prose an agent hand-maintains — invisible to the score.

## Proposed direction

Mike's framing: when a fresh memory pattern-matches an existing curated one, the existing entry gets a **+1** ("thumbs up") and the fresh one is folded in — so lessons reality keeps re-teaching auto-float to the top.

Mechanism:

- Add `reinforcement_count` (curator-mutable) as a **separate** field from `reference_count` — reads and re-learns are distinct signals; do not conflate.
- The existing `MERGE` action does the +1: on a **human-ratified** merge, bump the survivor's `reinforcement_count` (+1 per consolidation, or += the merged entry's own count) and record which generations contributed via a `reinforced_by:` lineage list (feeds the permanent-record principle — "A115, A124, A129, A135 all re-derived this").
- Feed `reinforcement_count` into the composite score as a new signal (its own weighted term, or through the doctrine's reserved multi-vote / anti-pin path). The scoring doctrine already lists "anti-pin," "multi-agent vote aggregation," and "adaptive thresholds" as planned v3.1 extensions — recurrence-as-implicit-upvote is a natural sibling.
- **Detect at curator-time, not write-time.** The +1 belongs where `MERGE` already lives (async, batched, off the critical path). Write-time matching would put a search + similarity judgment on the hot path every time an agent jots a note — against the "curator is never on the critical path" principle.

## Open questions

- **Similarity judgment is the crux.** The counter is only as good as "is this the same lesson?" The current saving grace: merges are already **human-ratified**, so every +1 is a confirmed thumbs-up, not an auto-guess. Is human ratification sufficient, or do we want a similarity heuristic (tag/topic/semantic) to *propose* candidates more aggressively? (Mike, 2026-07-20: not worried about runaways — the recurrence signal is welcome; log-compression on the counter is optional polish, not a gate.)
- **Score integration:** a dedicated weighted term vs. routing through the reserved Wilson/multi-vote path — which keeps the formula legible?
- **Seeding:** how to backfill `reinforcement_count` for existing hand-merged pins (e.g., Argus #1 = ~10 recurrences) so the new signal reflects history rather than starting everyone at zero?

## What this informs

A **v3.1 memory amendment**, not a redesign: the score-formula doctrine ([`5f2c1b94`](5f2c1b94.md) → v1.1, new signal) + the curator's `MERGE` action ([`50c0bdce`](50c0bdce.md) → increment + `reinforced_by:` lineage) + one new curator-mutable field on [memory.capsule `a5b3c891`](a5b3c891.md) + a validator check on the field. Informs a future dev-spec when the v3.1 slot opens.
