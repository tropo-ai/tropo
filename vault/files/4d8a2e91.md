# How Pipelines Work

**Relations**

| Relation | Target |
|---|---|
| Governed by | [Tropo Governance (8dd772a0)](8dd772a0.md) |

*A pipeline declares the shape of work you repeat; a pipeline-run executes one instance of it. The template lives in the Vault, the run records what actually happened.*

If you've used Airflow (DAG / DAG-run), BPMN (process / instance), or GitHub Actions (workflow / workflow-run), you already know the shape: you author the workflow once, you run it many times, and each run keeps its own record. A pipeline in Tropo is the same idea, written in plain markdown, governed by the Vault, and executable by any AI agent that can read files. It's how you capture the work you do *the same way every time* — a quarterly event, an onboarding sequence, a release — so the next instance plugs straight in instead of being reinvented.

## Template and instance — keep them apart

Two concepts, and the whole model rests on telling them apart.

- **Pipeline** — the template. A declaration of how the work flows: its stages, its steps, and the transitions between them. Versioned and reusable.
- **Pipeline-run** — one execution. It pins the template version at start, carries its own folder and event log, and is the audit trail for that one instance.

The split is what makes pipelines safe to evolve. Edit the template and new runs use the new version, while a run already in flight keeps the version it pinned. Delete a run and the template is untouched. Want to know what you actually did last year? Open that year's run folder; the events tell the truth.

## A pipeline is a tree of steps

A pipeline isn't a flat list — it's a small tree. The root is the pipeline; under it are **stages** (phases of the work); under those are **steps** (the leaves, where work actually happens). Every node is its own Vault entry (`type: pipeline`, `subtype: workflow-node`), and parents reference children by UID rather than nesting objects inline. Flow runs along each node's `next_steps:` — linear by default, one successor at a time. Nesting is soft-capped at three levels, a deliberate guard against the tangle that big workflow engines grow into.

## How a run executes

A pipeline-run doesn't run itself — it's a coordination-and-audit container, and the work is done by **processor-agents** operating inside it. The run's folder holds five files: `definition.md` (the steps), `context.md`, `thread.md`, `run.jsonl` (the append-only event log), and `run.state.json` (the resumption anchor). An agent reads the current step, does the work, appends a `step_completed` event, and the run advances to the next step along `next_steps`. A different agent can pick up the next step — the folder is the shared state, so the work survives the session.

The piece that makes this usable for real work is the **confirmation gate.** A step can declare `requires_confirmation: true`. When the run reaches it, the whole run pauses (`active → paused`) and writes a `pause_started` event; an authorized person appends `pause_resumed` with who approved, and the run picks up exactly where it stopped. That's how a workflow can hold for a human sign-off mid-flight — approve the budget before the invites go out — without anyone babysitting it.

Most pipelines are linear, but the schema goes further: a stage can **fan out** to run steps in parallel and **converge** when they all finish — Tropo's own release process uses this to run documentation and testing workflows side by side. Condition-based branching is still maturing; when in doubt, a straight line of steps is the right default.

## Pipeline or playbook?

Tropo also has [playbooks](2b5a3dd5.md) — governed step-by-step procedures an agent executes top to bottom. So when do you reach for a pipeline instead? Three things distinguish it:

- **State that survives the session.** A run carries its own folder, so you can pause it, walk away, and a different agent resumes it next week from exactly where it stopped. A playbook is run start-to-finish in one go.
- **Pauses for humans.** `requires_confirmation` gates let the workflow hold for an approval and continue afterward.
- **An audit trail by construction.** Every transition is an event in `run.jsonl` — replayable months later.

The rule of thumb: a **procedure you run once** → playbook. A **workflow with stateful execution that may pause for humans, span sessions, and leave an audit trail** → pipeline. And the honest test from the kitchen: if you wouldn't write down a recipe for it because you'll only cook it once, don't author a pipeline.

## How pipelines compose with the rest of Tropo

- **Tropo Work** — a pipeline is one of the four work primitives; it defines the stages a project moves through. See [How Tropo Work Works](2d4f8c91.md).
- **Playbooks** — a pipeline is the stateful, multi-session sibling of a playbook; both are governed procedures any agent can run.
- **Vault** — the template and every run are governed Vault entries; the event log is plain append-only markdown.
- **Agents** — processor-agents execute the steps; the run folder is the shared state that lets different agents hand off cleanly.
- **Channels** — the `run.jsonl` event log *is* the coordination trail: who did what, when, and who approved the gate.
