**What it does:**
1. Populates test-spec.closed_at with current ISO 8601 timestamp
2. Populates test-spec.acceptance_evidence with:
   - run-jsonl event UIDs from step 3 test_executed + test_aggregate events
   - coverage-audit UIDs from step 4 validate-coverage substrate
   - sa.* commissioning record UIDs where agentic_review fired
3. Flips test-spec.stage → done; test-spec.state stays active (only archives at supersession)
4. If test-spec.harness_framework_changes_required was true: populates test-spec.harness_extension_landed_evidence with substrate UIDs of harness extension that shipped as part of cycle scope per test-spec.capsule v1.0 §Harness Framework Changes — Triggers + Scope Expansion
5. Flips pipeline-run.status → done; writes terminal event to run.jsonl
6. **Back-feed:** updates triggering dev-pipeline activation's triggered_test_spec_uid field with this test-spec UID per engine extension [51d171f3] §Three-Pipeline Coupling State Machine. Engine's dev-pipeline activation close gate sees this back-feed + advances if doc-pipeline's parallel back-feed also landed.
7. Captures Mike approval signal verbatim (ship-bulletin pattern); records in activation entry close substrate

**What the engine does (separately, after step close):**
- Engine extension [51d171f3] §Three-Pipeline Coupling State Machine evaluates dev-pipeline activation's close gate
- If BOTH triggered_test_spec_uid + triggered_doc_spec_uid resolve to status:done test-spec + doc-spec entries → dev-pipeline activation can transition status:done (unblocks step 6 produce-release-folder for the triggering dev-cycle)
- If either still in-flight → dev-pipeline activation stays BLOCKED until parallel-pipeline closes

## DSL rewrite note (Talos, 2026-07-04, 4f87d056/0fa72100)

Six replacements, four handle/judgment calls beyond Argus's pre-authored text:

- **Handle name:** `test_spec` (underscore) is the bound context handle — confirmed by reading `build_run_context_uids` in `9e7003b1.py`, which had NO handle at all for a test-pipeline activation's own test-spec (it only ever built `dev_spec`/`triggered_test_spec` from the DEV side). Added the reverse-resolution branch (parses `triggered-by-dev-cycle:<uid>` out of this activation's `cycle_context`, reads that dev-cycle's `dev_spec_uid`, then that dev-spec's `triggered_test_spec_uids[0]`) so `test_spec` now resolves for every test-pipeline run. Same fix adds `doc_spec` for doc-pipeline activations, symmetrically.
- **Back-feed criterion:** `triggering dev-pipeline activation's triggered_test_spec_uid field` does not exist anywhere in the substrate — no such field is ever written on the activation entry itself. The REAL field the engine's own close-gate reads (`check_triggered_pipeline_completion` in `9e7003b1.py`) is `triggered_test_spec_uids` (plural) on the triggering DEV-SPEC, pre-populated at trigger-step time (confirmed: `fc4874f4.triggered_test_spec_uids == [0c9dbe07]` already, for this run). Added a `triggering_dev_spec` context handle (same reverse-resolution as `test_spec` above) and rewrote the criterion against the field that's actually there. `contains <test_spec>` (Argus's bracketed alternative) is not viable as written — the grammar's `contains` right-hand side is a literal string, never handle-resolved, so it can't be made to compare against another handle's resolved value; `populated` against the real field is the honest, template-safe check.
- **DROPPED, flagged to Argus (genuine DSL-extension cases, not silently worked around):**
  - `if test-spec.harness_framework_changes_required: test-spec.harness_extension_landed_evidence populated` — a conditional ("if X then Y") criterion; the grammar has no conditional form. For this run `harness_framework_changes_required` is absent/false, so the condition never fires, but the DSL can't express "vacuously true when X is falsy" without either a new `implies:` shape or splitting into a separately-authored non-gating note.
  - `pipeline-run.status = done; pipeline-run.run.jsonl terminal event written` — describes a POSTcondition of `action_complete_workflow` itself (which sets `pipeline-run.status` and writes the terminal event AFTER this step verifies, not before) — checking it as a precondition of verifying step 5 is circular. Already true-by-construction once `complete-workflow` runs; not a step-5 gate.
- **`Mike approval signal captured...` → `human:047c147c`** — NOT a DSL-extension case; this is the engine's existing `human:` dispatch (added since the v1.62 dogfood), which already implements exactly this shape (an independent, step-scoped, non-self `human_signoff` with an accepted verdict). No prior version of this step used it; it should have from the start given `trust_level: approval-required`.
