# How Projects Replace Folders

*In Tropo, projects are the organizational unit — not folders. The question stops being "where does this file go?" and becomes "which project owns this?"*

This is the single most important shift in how Tropo organizes work, and it's worth slowing down on. Every tool you've used before — Drive, Notion, SharePoint, a folder on your laptop — makes you answer the same question every time you create something: *where do I put this?* You build a folder tree, you place each file in exactly one spot, and the tree becomes the organization. Tropo doesn't have a folder tree for your work. It has flat storage and it has projects, and the only question that matters is which project owns the thing.

## The old question and the new question

In a folder system, a file's location *is* its meaning. Marketing docs go in `Marketing/`. Event plans go in `Marketing/Events/2026/`. To find something, you navigate the tree; to file something, you decide where it lives — once, and you live with the choice. The structure is rigid by design, and it breaks in predictable ways: a file relevant to two teams has no good home, a reorg means everything moves, and a new hire who doesn't know the conventions can't find anything.

In Tropo the file's location carries no meaning at all. Every governed file lives at `vault/files/<uid>.md` — a flat address that tells you nothing about what the file is or who cares about it. Meaning comes from **project membership**: a file declares `member_of: [<project-uid>]`, and the project is the thing that says "this is mine, for this purpose, alongside these other files."

## One file, many homes

The reference model unlocks the thing folders never could: **a file can belong to more than one project at once, with no copies.** A folder forces you to pick — the save-the-date for the customer event is *also* the canonical example in your brand guidelines, so which folder wins? In a folder system you copy it, and now you have two files that drift apart. In Tropo the file has one UID and one home in the Vault, and both projects list it in their membership. One file, two organizational contexts, zero duplication.

## You open a project, not a folder tree

Because location carries no meaning, you never navigate to work — you open the project that owns it. A project is a container with a name and a purpose, and opening it shows you everything that's `member_of` it: the tasks, the decisions, the documents, regardless of where any individual file physically sits. The project's **board** is just a live view of its tasks grouped by status — it isn't a stored file you maintain, it's rendered on demand from the membership. You don't keep the board in sync; it's computed from the work underneath, so it can't lie.

## A working day — the 2026 Customer Event

Here's the shape of it in practice. You start by naming the work, not by picking a folder — *"I want a project for the 2026 customer event."* Your agent creates the project entry and you're ready to add work. When a document comes up — a save-the-date, a venue contract, an agenda — you don't decide where it goes; you say what it's for: *"add the save-the-date to the customer event project,"* and the agent authors the file in the Vault `member_of` the project. When that same save-the-date turns out to be the canonical example for the brand guidelines too, you don't copy it — you add the second membership, and both projects show it.

Six months later, finding any of it is the same one move every time: open the project. Its board shows what's active; its membership shows everything it owns. Nobody navigates a tree, nobody remembers a convention, and nothing was filed in the wrong place — because there was no place to file it in, only a project to assign it to. This public studio ships with real projects you can open and read this way — e.g. `e8d1a4f6` ("Hello Tropo — 2026 Customer Event Plan") and `1a17e001` ("Lantern — Monthly Newsletter Planning").

## The new habit

When you're about to create something — a document, a task, a decision — the question is never "where does this go?" It's:

1. **Which project owns this?** If one exists, the file joins it by reference.
2. **Does the project exist yet?** Ask your agent, or query the Vault index for `type:project state:active`.
3. **If not, start one.** A new project is created by naming it; the work gets a home, and the board renders itself from whatever you put in it.

The project is the answer to "where does this go." Always.

## How this composes with the other primitives

- **Vault** — flat storage at `vault/files/<uid>.md` is what makes this possible: because location carries no meaning, membership is the only organization, and one file can belong to many projects.
- **Tropo Work** — projects are one of the four work primitives; tasks live `member_of` a project and its board rolls up from them. See [project.capsule (34e4cb0b)](34e4cb0b.md) and [task.capsule (3289712a)](3289712a.md) for the contracts.
- **Agents** — agents own projects and operate their boards; when an agent boots, it orients on the project boards it owns, not a folder tree.
- **Capsules** — `project` is a governed type with its own lifecycle (`stage: ideate → build → done`); the rules travel with the file.
- **Channels** — every membership change and task move emits an event, so a project's history and its coordination are the same trail.
