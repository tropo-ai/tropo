# plan-test-substrate — test-pipeline step 1

<!-- nav-block:start -->
**📍 Vault Path:** [tropo-work](b8e5f3a2.md) → [test-pipeline](da3f50dc.md) → [prepare — test-pipeline stage](69c291b7.md) → **plan-test-substrate — test-pipeline step 1**

*Planning step. Vela authors plan substrate naming each behavior's test substrate path + verification_method dispatch shape before any test substrate is authored or run.*

**Why this step exists:** the plan is the bridge between test-spec declaration (what behaviors will be covered) and execute stage (authoring + running). Without an explicit plan, step 2 + step 3 happen without coherent per-behavior orchestration. The plan substrate becomes the working document the execute stage consumes.

**What it does:**
1. Loads test-spec entry (already validated at step 0)
2. For each behaviors_covered entry, authors a plan section:
   - behavior_description (mirrors test-spec)
   - test_substrate_path resolution (file exists at path → confirm; OR new-file → flag for step 2 authoring)
   - verification_method dispatch shape:
     - `machine_executable_script` → command line to invoke at step 3; expected exit code semantics
     - `deterministic_assertion` → DSL expression evaluation grammar per pipeline.capsule v3.0 §6
     - `structural_check` → validator extension name; tropo-validate.py invocation
     - `agentic_review` → sa.* class to dispatch (dispatch_target field) + commissioning record path + [QUERY]/[RESPONSE] protocol
     - `manual_walk` → Mike-readable walk prompt + acceptance criterion
   - target_substrate_refs (mirrors test-spec; cross-validation reference)
3. Flags harness_framework_changes_required if any verification_method requires runner/library/aggregator extension per test-spec.capsule §Harness Framework Changes — Triggers + Scope Expansion
4. Writes plan substrate to workspace path; pipeline-run references the path

**Hands off to:** step 2 author-test-substrate.

## DSL rewrite note (Talos, 2026-07-04, 4f87d056/0fa72100)

**Judgment call (flagged by Argus):** `file:` criterion paths are taken LITERALLY by the engine (`evaluate_criterion`'s `file_exists` branch did `is_file()` on the path text as-is) — no `<activation-uid>`-style substitution existed, so the original prose's `<activation-uid>` placeholder would never have matched a real per-run file even if the surrounding text had parsed as DSL. Rather than resort to a handle-based existence check (no `test_plan` UID-registered artifact exists — the plan is a raw file, not a vault entry), added `{handle}` token substitution to the `file:` evaluation path — the SAME substitution mechanism `verification_command` already had (`9e7003b1.py`, `_vc_str.replace("{" + h + "}", ...)`), just applied to the second call site that lacked it. `file:...test-plan-{activation}.md.exists` now resolves correctly per-run from the `activation` handle every run already has.

The four remaining prose lines (per-behavior breakdown, section-naming, `agentic_review` dispatch-target naming, harness-changes flagging) describe qualitative CONTENT requirements of the plan file, not a field/existence check the grammar can express, and are — verbatim — the body's "What it does" list above; nothing is lost by dropping them from the machine-evaluated list. This step is `verification_class: false` (never DSL-gated in the first place, at either `step-complete` or `verify-step`), so leaving them as prose was harmless; converting the one criterion that COULD be made real (the plan file's existence) is the improvement that matters here.
