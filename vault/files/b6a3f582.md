# Tropo for Enterprise Evaluators — FAQ

*For technical leaders, security teams, and compliance officers assessing Tropo for team or organizational adoption. Five questions enterprises actually ask, with direct answers.*

---

## 1. "What's the governance contract?"

Tropo's governance is explicit, file-based, and inspectable end-to-end.

The model is **four files in three tiers**:

- **OS-tier (two files)**: `AGENTS.md` (at the Studio root and in key governed folders; cross-platform entry point) + `TROPO-CONTROL.md` (the kernel: universal invariants that apply in every Tropo Studio — UID requirement, governance file requirements, operations logging, registry tracking, OS read-only protection).
- **Studio-tier (one file)**: `STUDIO.md` at the Studio root + companion `.tropo-studio/operating-principles.md` — your organization's defaults and constraints: registration policy, write scopes, agent class rules, custom invariants.
- **Folder-tier (one file per folder)**: `CAPSULE.md` — folder-specific purpose, access control, and operating logic. Each governed folder declares who can write, what belongs, and what protocols apply.

The override contract is explicit: TROPO-CONTROL.md invariants override STUDIO.md; STUDIO.md overrides CAPSULE.md. Nothing slips in unannounced.

Every governed artifact also has a typed contract (a `capsule` — see the [How Capsules Work](5f7a9d83.md) KB). The capsule declares the type's schema, its state machine, validation rules, and what changes require explicit approval. Each capsule defines its own state machine; there's no universal lifecycle. Validation runs via `python3 vault/tools/tropo-validate.py --customer` — exit code 0 = clean, after the one-time index build that `START-TROPO.md` names (`python3 vault/tools/tropo-rebuild-index.py --apply`). The flagless form adds release-time gates that do not apply to a customer Studio and will report failures on a healthy one.

If a rule needs to change, the change itself is a governed artifact (a decision, an ADR, an amendment to the capsule). Nothing slips in unannounced.

## 2. "How do I audit changes?"

Five audit surfaces, each independently verifiable. The event ledger, packing slip, and governed frontmatter are present in the box you downloaded; lineage files and recycle receipts are created the moment those acts first happen:

- **The event ledger** — `vault/events/00-events.jsonl` ships with the studio and grows from the moment your first agent activates. Every governed action lands as a structured record: agent-to-agent messages, crew broadcasts, file modifications, soft-deletes, validator runs, release acts — each with type, actor, timestamp, and payload. Human-readable in any text editor; queryable with the bundled `vault/tools/tropo-query-events.py`. It is append-only by design.
- **Agent lineage** — every agent session is a generation, recorded as one immutable line in `agents/<slug>/lineage.jsonl` by `vault/tools/tropo-lineage.py` at birth and at retirement: who activated, which agent, what generation, when. A retiring generation leaves a transfer letter at `agents/<slug>/transfers/<GEN>.md` — a durable record of what each generation knew and handed forward. Each activation or retirement executes as a governed playbook run, which leaves its own append-only `run.jsonl` event log in a `playbook-runs/<run>/` folder (a required file under the playbook-run capsule). The canonical roster of registered agents sits beside it at `.tropo-studio/registries/agent-registry.yaml`.
- **The packing slip** — `MANIFEST.md` and `tropo-image-manifest.json` list every file in the box with sizes and SHA-256 hashes. Verify the studio you received is byte-for-byte the studio that shipped, with one command. (Working surfaces like the event ledger grow with use, by design — the manifest records the shipped state.)
- **Governed frontmatter** — every artifact carries its identity in its own bytes: `uid`, `owner`, `created`, `modified`, lifecycle state. Query surfaces like `vault/00-index.jsonl` are derived and regenerate from this frontmatter on demand (`vault/tools/tropo-rebuild-index.py`) — audits read the source files, never a projection that could drift from them.
- **Recycle receipts** — deletion is never `rm`. `vault/tools/tropo-recycle.py` soft-deletes into `recycle/agent-deletions/<date>/` with the reason recorded on the event ledger, so even removals are audited acts and recoverable artifacts.

Put the studio in your own git repo (the normal configuration) and you add `git log` / `git blame` attribution on top — the box itself is a folder, and version control is yours to point at it.

For incident review: query the event ledger by event type, actor, or position in the log with `tropo-query-events.py` (`--type`, `--party`, `--since-id`); walk an agent's lineage file for its session history; read any artifact's frontmatter for its provenance.

For continuous audit: standard CI can run `python3 vault/tools/tropo-validate.py --customer` on every commit and surface drift before it lands. **Build the index in the same job first** (`python3 vault/tools/tropo-rebuild-index.py --apply`) — the index is a machine-local product that is deliberately not committed, so a checkout without it produces index-derived failures that look like drift and are not. With the index built, exit code 0 = clean.

## 3. "Can my team run this with our own data?"

Yes. Tropo is filesystem-local and runs entirely within whatever environment you put it in.

- **No external dependencies** — Tropo doesn't phone home, doesn't require an API key, doesn't ship telemetry. The LLM you use is the only external surface, and you choose which one.
- **Local-first by design** — Tropo vaults are folders on disk. Sync via git, sync via your enterprise file system, sync via whatever your team uses. No SaaS dependency.
- **Your data stays where you put it** — agent-authored files live at `vault/files/<uid>.md` on your filesystem. Whatever data-handling policies apply to your other filesystem content apply here.
- **Air-gapped operation** — if your LLM runs locally (Llama, your own fine-tuned model, etc.), Tropo runs fully offline.

For sensitive workloads: place the Tropo vault inside your existing data-classification boundary. The vault inherits whatever protections that boundary provides.

## 4. "What about compliance?"

Tropo's compliance posture is "the substrate is auditable; the runtime is your choice."

- **SOC 2 / ISO 27001** — Tropo doesn't directly implement these frameworks, but its file-based + append-only + git-versioned design composes cleanly with them. Your existing controls (access management, encryption-at-rest, change-management) apply to Tropo files the way they apply to any other markdown in your repos.
- **HIPAA / data-residency** — Tropo doesn't transmit your data anywhere. The LLM you run is the only data-egress point; choose one that meets your requirements (on-premise model, BAA-covered API, etc.).
- **Audit trails** — the event ledger + agent lineage + SHA-256 packing slip give you a triple-recorded audit surface that's stronger than most SaaS tools provide: what happened (events), who did it across sessions (lineage), and exactly what shipped (hashes). All three are plain files in the box, inspectable without any Tropo tooling.
- **Right-to-be-forgotten** — every governed file is markdown; deletion is `tropo-recycle.py <uid>` (soft-delete to a recycle folder) or `git rm` (hard-delete from history). Both are auditable.

What Tropo doesn't claim: certified compliance with specific frameworks. What it provides: a substrate your compliance team can inspect, attest to, and integrate into your existing posture.

## 5. "How does this work at multi-team scale?"

Today's model is one Studio per team, at any team size, with cross-Studio composition available via vault mounts.

Within a single Studio:

- **Multiple agents coordinate via the typed event log** — each agent has its own scope (charter), its own files, its own memory. Agents coordinate through structured events (`vault/tools/tropo-emit-event.py` / `tropo-query-events.py`) on the shared ledger; `channels/` holds user-facing projection surfaces. Coordination is auditable.
- **Multiple humans share a Studio** — git-based collaboration. Standard PR/review workflow. Multiple humans can direct multiple agents in parallel; the vault tracks who did what.
- **Multiple work-streams compose via projects + pipelines** — each project owns its own work; pipelines define repeatable workflows; the dev-pipeline pattern (used by Tropo itself) shows how to compose them.

Across multiple Studios:

- **Vault mounts** — a Studio can mount another vault with `python3 vault/tools/tropo-mount.py`: the mount validates the candidate vault's manifest, pins it to a resolved commit hash in `.tropo-studio/compose.lock`, and requires explicit consent recorded as a governed write.
- **Cross-vault merge + governance gate** — reference implementations of the field-aware merge driver and the governance validator gate ship at `vault/tools/federation/` (documented there as reference-grade, not yet production-wired).

For enterprise adoption today: start with one Studio per team; compose across teams via vault mounts as the need arises.

## When this FAQ doesn't answer your question

The architectural source-of-truth lives in the substrate itself. For governance specifics: read `.tropo/TROPO-CONTROL.md` + your Studio's `STUDIO.md`. For audit specifics: run `python3 vault/tools/tropo-validate.py --customer` and inspect the event ledger at `vault/events/00-events.jsonl`. For compliance integration: bring your compliance team into a working Tropo Studio and let them inspect the substrate directly — the design principle is "you can read every rule that applies to your data."
